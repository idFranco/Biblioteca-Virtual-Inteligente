# SOP: qa-check

Execute the following steps STRICTLY in order for the provided story. If any tool fails, stop immediately.

1. **MANDATORY:** Invoke `index_repository` with path `.`.
2. Review changes and validate all acceptance criteria of the story.
3. **GET BRANCH:** Execute `git branch --show-current` and save the exact name.
4. **STATUS BRANCH:** If any criterion fails, invoke `project_memory_advance_status` to 'Rejected', document the failure in the story `.md` file, and STOP. Emit exactly: *"QA validation failed for $ARGUMENTS. Story set to Rejected. To fix and retry, execute: implement-user-story $ARGUMENTS"*.
5. **STRICT DOCUMENTATION:** Explicitly replace the text 'Pending' in the 'QA Result' section of the story `.md` file with the actual results. Do NOT modify '## Implementation Notes' — that section is owned by `implement-user-story` and should already be filled in; if it still reads 'Pending' at this point, treat that as a QA failure (documentation gate not met) rather than filling it in yourself. MANDATORY: Create or update the iteration log in the root of `workflow/opencode/ai-engineering/` with this story's QA results. For the filename, replace any slashes `/` in the branch name with dashes `-` (e.g., `feature-US-001-base-setup.md`). You are PROHIBITED from creating subfolders. This iteration log is owned by QA — populated automatically on every `qa-check` run; Technical Writer may enrich it later with narrative context but must not overwrite QA's recorded results.
6. **PRE-PUSH VIA MCP:** Execute `git status --porcelain` to identify ALL modified or untracked files (documentation, `project_state.json`, and any other files touched by side MCPs). Invoke `push_files` with that full list. Then execute `git fetch origin` and `git reset --hard origin/<branch-name>` (replacing with the exact name).
7. **CREATE PR (PR GATE):** Use EXCLUSIVELY the GitHub MCP `create_pull_request` tool. If the tool fails or returns an error, STOP IMMEDIATELY. Do not advance the status. Emit exactly: *"PR creation failed. Story NOT marked as Validated. Fix the GitHub MCP error and re-run qa-check $ARGUMENTS"*.
8. **MERGEABILITY CHECK (PRE-PR):** When creating the Pull Request in step 7 via the `create_pull_request` MCP tool, verify the "mergeable"/conflict status returned by the GitHub MCP response.
    - **If mergeable:** continue normally to step 9.
    - **If NOT mergeable (conflicts with main):** STOP IMMEDIATELY. Do not attempt to resolve conflicts with local git. Emit exactly: *"Pull Request created but has conflicts with main. Please resolve them via GitHub (or ask a maintainer) before merging. Once resolved, re-run qa-check $ARGUMENTS if further changes are needed, or merge manually once conflicts are cleared."* Do not advance the status to Validated until the PR is effectively mergeable.
9. **STATUS ADVANCEMENT:** ONLY IF the PR was successfully created in step 7 and was mergeable in step 8, MANDATORILY invoke the `project_memory_advance_status` tool to change the status to 'Validated'.
10. **FINAL PUSH VIA MCP:** Since the previous step modified local memory and story files, MANDATORILY invoke `push_files` a second time to upload all modified or untracked files in the working directory to the PR's remote branch.
11. **LOCAL TREE SYNC:** Execute in the terminal `git fetch origin` and then `git reset --hard origin/<branch-name>` so that your local working tree becomes exactly identical to the remote.
12. **CLOSURE AND NOTIFICATION:** Emit EXACTLY this final block: *"The QA phase for $ARGUMENTS is complete and the PR has been created. To merge and close this story, review and merge the Pull Request on GitHub."*
