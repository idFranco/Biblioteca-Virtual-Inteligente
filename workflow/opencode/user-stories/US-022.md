# User Story — US-022 — Corregir build de Docker del backend por referencia al proyecto de tests en la solución

*(Possible statuses: Draft, Planned, Approved, In Progress, Implemented, Validated, Rejected)*

## User Story

Como administrador del proyecto, quiero que el Dockerfile del backend copie también el .csproj del proyecto tests/BibliotecaVirtual.Tests/ en la capa de restaurar dependencias (como ya hace con los 4 proyectos de src/), para que docker compose up --build resuelva todos los proyectos referenciados por BibliotecaVirtual.slnx y el stack completo levante sin el error MSB3202.

---

## Functional Description

`docker compose up --build` falla en el stage de build del backend con el error:
`MSB3202: The project file "/src/tests/BibliotecaVirtual.Tests/BibliotecaVirtual.Tests.csproj" was not found. [/src/BibliotecaVirtual.slnx]`.

Causa raíz: US-021 añadió el proyecto de tests `tests/BibliotecaVirtual.Tests/` y lo registró en `BibliotecaVirtual.slnx`. El `Dockerfile` del backend (build stage, capa de `dotnet restore` para cache) solo copia el `.slnx` y los 4 `.csproj` de `src/`; no copia el `.csproj` del proyecto de tests, por lo que `dotnet restore` (que restaura toda la solución, al no pasar argumento de proyecto) no resuelve la referencia a solución y aborta el build.

Solución: añadir una línea `COPY` del `.csproj` del proyecto de tests en la capa de restore, antes de `RUN dotnet restore`, siguiendo el patrón existente de los 4 proyectos de `src/`. Como `dotnet publish src/WebAPI/BibliotecaVirtual.WebAPI.csproj` (siguiente capa) apunta solo al proyecto WebAPI, el proyecto de tests NO se incluye en la imagen runtime — no se requiere ningún otro cambio en el Dockerfile.

Se verificó que ni el Dockerfile de frontend ni el de chatbot presentan este bug (usan build monocarpeta, sin archivo de solución), y que el `.dockerignore` del backend (contexto de build) no excluye `tests/`.

## Technical Plan

### Cambio único — `workflow/backend/Dockerfile`

Insertar una línea `COPY` del `.csproj` del proyecto de tests después de la línea 8 (`COPY src/WebAPI/...`) y antes de la línea 9 (`RUN dotnet restore`):

```dockerfile
COPY tests/BibliotecaVirtual.Tests/BibliotecaVirtual.Tests.csproj tests/BibliotecaVirtual.Tests/
```

Bloque resultante del build stage (líneas 4-9):

```dockerfile
COPY BibliotecaVirtual.slnx ./
COPY src/Domain/BibliotecaVirtual.Domain.csproj src/Domain/
COPY src/Application/BibliotecaVirtual.Application.csproj src/Application/
COPY src/Infrastructure/BibliotecaVirtual.Infrastructure.csproj src/Infrastructure/
COPY src/WebAPI/BibliotecaVirtual.WebAPI.csproj src/WebAPI/
COPY tests/BibliotecaVirtual.Tests/BibliotecaVirtual.Tests.csproj tests/BibliotecaVirtual.Tests/
RUN dotnet restore
```

No se requiere ningún otro cambio:
- `dotnet publish src/WebAPI/BibliotecaVirtual.WebAPI.csproj` (línea 12) apunta solo a WebAPI; el proyecto de tests y sus paquetes xunit NO llegan a la imagen runtime (la capa runtime hace `COPY --from=build /app .`).
- `COPY . .` (línea 11) ya trae el código fuente completo (incluida `tests/`) para la capa de publish.
- El `.dockerignore` en el contexto de build (`workflow/backend/.dockerignore`) no excluye `tests/`.
- Los `ProjectReference` del proyecto de tests (`Application`, `Domain`, `Infrastructure`) ya están copiados en la capa de restore, por lo que restore los resuelve.
