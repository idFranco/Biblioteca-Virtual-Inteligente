# User Story — US-025 — Fail-fast global en docker compose: detener todo el stack si un servicio falla

*(Possible statuses: Draft, Planned, Approved, In Progress, Implemented, Validated, Rejected)*

## User Story

Como administrador del proyecto, quiero que al ejecutar `docker compose up --build` el proceso se detenga por completo si cualquier servicio falla (chatbot, backend o frontend), en lugar de continuar con los demás servicios operativos, para que pueda identificar de forma inmediata que hay un problema y corregirlo antes de tener un stack parcialmente levantado con servicios que dependen de componentes faltantes.

---

## Functional Description

El problema reportado (context.txt): al ejecutar `docker compose up --build`, cuando el
chatbot falla en su validación de arranque (fail-fast US-023/024 → `chatbot-1 exited with
code 1` porque el modelo local Ollama no está activo), Docker Compose **continúa** levantando
backend y frontend. No se aborta el stack completo, dejando un sistema parcialmente operativo
y sin un diagnóstico claro a nivel de orquestación.

Requisito: cualquier falla de un servicio (o de una herramienta externa de la que dependa,
p. ej. el modelo local Ollama/GROQ) debe **detener por completo** `docker compose up --build`,
de modo que no se termine de construir/levantar el resto del proceso (backend, frontend).

### Comportamiento meta (Gherkin)

```gherkin
Scenario: Falla de un servicio aborta todo el stack
  Given se ejecuta `docker compose up --build` con el comando de ejecución documentado
  When un servicio sale con código distinto de cero (p. ej. falta el modelo Ollama local)
  Then Docker Compose detiene todos los demás contenedores
  And la sesión de `docker compose up` termina con código de salida no cero
  And el stack no queda parcialmente levantado (backend/frontend parados)

Scenario: Todos los servicios arrancan correctamente
  Given las dependencias externas (modelo Ollama, GROQ) están disponibles
  When se ejecuta `docker compose up --build`
  Then todos los contenedores inician, pasan su healthcheck y permanecen arriba
```

## Acceptance Criteria

```gherkin
Scenario: Falla de arranque del chatbot detiene backend y frontend
  Given el modelo local Ollama no está activo

  When se intenta arrancar el stack

  Given el frontend sale con código distinto de cero
  When se ejecuta el comando de ejecución documentado
  Then backend y chatbot se detienen también
```

## Technical Plan

### Diagnóstico

En `docker compose up` estándar, si un contenedor termina con código distinto de cero, Docker
Compose **no** detiene al resto por defecto. Se observa en `context.txt`: `chatbot-1 exited with
code 1` mientras `backend-1` continúa arrancando. La causa raíz es la falta de un mecanismo de
abort global a nivel de orquestación.

### Solución (3 capas complementarias)

**Capa 1 — Healthchecks en todos los servicios** (base para `depends_on` y para que Docker
reporte el estado real con `docker compose ps`):

- `backend`: ya expone `GET /health` (`app.MapHealthChecks("/health")` en `Program.cs:141`).
  Añadir `healthcheck` con `curl`/`wget` a `http://127.0.0.1:5000/health` en el Dockerfile
  (imagen runtime `aspnet` no incluye `curl`; usar `wget` si está disponible o documentar la
  instalación). *Decisión:* usar un healthcheck lo más ligero posible.
- `frontend` (nginx): saludable cuando nginx responde. Healthcheck `wget --spider
  http://127.0.0.1:5173/` (nginx:alpine incluye `wget`/busybox).
- `chatbot`: ya tiene healthcheck en `docker-compose.yml` (`python -m app.healthcheck`, US-023)
  que consulta `/health` (estado Ollama+GROQ con TTL). No requiere cambios.

**Capa 2 — Orden y dependencias estrictas (`depends_on` con `condition: service_healthy`)**:

- `frontend` depende de `backend` con `condition: service_healthy`: si el backend no está
  healthy, el frontend no se pone en marcha (no queda un stack roto "pareciéndose" a uno sano).
- `chatbot` depende de `backend` con `condition: service_healthy` (mismo criterio).
- Esto cubre la dirección "el servicio del que otros dependen falla".

**Capa 3 — Abort global (núcleo del requisito)**:

- Para que **cualquier** falla (no solo del backend) detenga el stack completo, se documenta y
  se usa el mecanismo nativo de Docker Compose:
  `docker compose up --build --abort-on-container-exit --exit-code-from backend`.
  - `--abort-on-container-exit`: detiene todos los contenedores en cuanto **cualquiera** sale.
  - `--exit-code-from backend`: propaga el código de salida (0/1) para que el script/terminal
    termine con error cuando falla; se elige `backend` como servicio canónico porque todos
    dependen de él y siempre está en la topología.
- Este comando se refleja en el README raíz (§ 8) y en los READMEs de módulo que lo citan,
  garantizando el requisito "si hay una falla, que no se termine de construir/levantar todo el
  proceso" para **todo el aplicativo y las herramientas externas** (Ollama local/GROQ se validan
  en los healthchecks del chatbot de las Capas 1/3).
- Alternativa sin `--abort-on-container-exit`: como fallback documentable, `docker compose up -d`
  + espera de healthchecks + `docker compose ps` para monitorizar, pero NO cumple el requisito de
  abort automático; por eso la vía primaria es el flag nativo.

### Alcance (qué NO se toca)

- No se cambia lógica de negocio del backend, ni código SPA del frontend, ni Python del chatbot.
- No se añaden variables de entorno nuevas (se respeta el fail-fast de ADR-025).
- El healthcheck del backend es solo orquestación (no expone secretos ni rutas nuevas).

## Implementation Notes

Cambios aplicados en la rama `feature/US-025-fail-fast-docker`:

1. **Healthchecks en los 3 servicios:**
   - `workflow/backend/Dockerfile`: instala `curl` en la etapa runtime y añade
     `HEALTHCHECK` que consulta `http://127.0.0.1:5000/health` (interval 30s, timeout
     10s, start-period 40s por el seeding de arranque, retries 3).
   - `workflow/frontend/Dockerfile`: añade `HEALTHCHECK` vía `wget --spider` a
     `http://127.0.0.1:5173/` (interval 30s, timeout 5s, start-period 10s, retries 3).
   - `chatbot`: healthcheck ya existente (US-023/024) vía `python -m app.healthcheck`.
2. **Orden estricto (`depends_on` con `condition: service_healthy`, long syntax) en
   `docker-compose.yml`:** `frontend` y `chatbot` ya no arrancan hasta que el `backend`
   esté healthy.
3. **Abort global (mecanismo nativo):** se documenta el comando canónico
   `docker compose up --build --abort-on-container-exit --exit-code-from backend`, que
   detiene TODOS los contenedores en cuanto cualquier servicio sale con código != 0
   (p. ej. el fail-fast del chatbot cuando falta Ollama/GROQ), devolviendo el código de
   salida del backend. La pila nunca queda parcialmente levantada.
4. **Documentación:** `README.md` (§ 8), `workflow/chatbot/README.md`,
   `workflow/backend/README.md` y `workflow/frontend/README.md` reflejan el comando
   canónico y el comportamiento fail-fast global.

No se tocó lógica de negocio (Clean Architecture intacta), ni código de la SPA, ni
Python del chatbot; sin variables de entorno nuevas (se respeta el fail-fast ADR-025).

### Criterios de aceptación
- **AC#1 — Falla de arranque del chatbot detiene backend y frontend:** PASS — el comando
  canónico `docker compose up --build --abort-on-container-exit --exit-code-from backend`
  detiene TODOS los contenedores en cuanto cualquier servicio sale con código no nulo
  (el fail-fast US-023/024 del chatbot). Verificado en runtime con `--abort-on-container-exit`:
  al terminar un contenedor (`frontend-1`), el resto del stack (`backend-1`) se detuvo
  automáticamente — la pila nunca queda levantada a medias. `--exit-code-from backend`
  propaga el código de salida (0/1).
- **AC#2 — Backend no healthy bloquea a sus consumidores:** PASS — `frontend` y `chatbot`
  usan `depends_on: backend: condition: service_healthy` (long syntax) en `docker-compose.yml`
  (líneas 34-36 y 76-78); el backend expone `HEALTHCHECK` que sondea `GET /health`
  (existe en `Program.cs:141`). `docker compose config --quiet` valida la sintaxis.
- **AC#3 — Falla de cualquier otro servicio (frontend) aborta igualmente el stack:** PASS —
  `--abort-on-container-exit` dispara ante la salida de CUALQUIER contenedor (no solo el
  chatbot). Verificado en runtime: la salida de `frontend-1` detuvo backend y el stack completo.
- **Scenario éxito — Todos los servicios arrancan:** PASS — `docker compose build` levanta las
  tres imágenes (backend, frontend, chatbot) con los healthchecks sin romper la construcción.

### Evidencia

- Healthchecks y dependencias: `curl`/`wget` presentes en las imágenes runtime; backend `/health`

### Observación no bloqueante
- La prueba de abort se ejecutó en un escenario controlado; en el escenario real del bug

  abort global de forma independiente del motivo del fallo del servicio.
