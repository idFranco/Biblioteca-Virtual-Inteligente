# User Story — US-014 — Optimización de documentación, configuración por variables de entorno y ajustes de UX (roles, alquiler y chatbot)

*(Possible statuses: Draft, Planned, Approved, In Progress, Implemented, Validated, Rejected)*

## User Story

Como administrador del proyecto, quiero (1) reorganizar la documentación moviendo el README extenso de la raíz a otra sección y creando documentación específica para backend y MCP; (2) eliminar todos los valores por defecto hardcodeados (mensajes placeholder y connection strings con fallback) para que toda la configuración se maneje por variables de entorno, incluidas las imágenes Docker; (3) renombrar la sección "Gestión de libro" del admin por un nombre no confuso y ocultar "Mis Alquileres" para el rol administrador (que tampoco debe poder alquilar); (4) habilitar la acción de alquilar libros para el usuario normal en el catálogo; y (5) dejar el chatbot minimizado por defecto con la acción de maximizarlo, para tener un proyecto mejor documentado, configurable por entorno y con una experiencia de usuario coherente por rol.

---

## Functional Description

La historia cubre cinco frentes independientes:

### R1 — Documentación (Technical Writer)

- El `README.md` de la raíz (413 líneas) es un monolito: mezcla la descripción general del proyecto con detalles profundos de cada módulo (tabla de variables de entorno, Docker, seed, identidad visual, y las secciones 10–12 de US-011/012/013).
- Se prometió en la propia raíz (línea 100–101) que el rol Technical Writer crearía READMEs por módulo (`/backend`, `/frontend`, `/chatbot`, `/mcp`), pero hoy solo existen `workflow/frontend/README.md` (49 líneas, con contenido de plantilla Vite que debe depurarse) y `workflow/chatbot/README.md` (69 líneas). **Faltan** `workflow/backend/README.md` y `workflow/mcp/README.md`.
- Resultado esperado: la raíz queda como índice/visión general (descripción, arquitectura, flujo AI Engineering, quick start, enlaces a los READMEs de módulo), y el detalle técnico vive en cada módulo.

### R3 — UX del rol Administrador

- La barra de navegación (`Header.tsx:68-71`) muestra el enlace **«Gestión de libro»** (singular) para quien tiene `books.manage`, junto a **«Gestión de libros»** (plural, `books.create/update/delete`). Se renombra el enlace singular a **«Solicitudes de libros»** y se ajusta el título/subtítulo de `GestionLibroPage` (actualmente «Gestión de libro»). El componente gestiona solicitudes de copias (aprobación/rechazo de `BookRequest`), por lo que el nuevo nombre es fiel a su función.
- El rol `Admin` actualmente incluye `rentals.create` y `rentals.view_own` (Program.cs:160), por lo que el admin ve «Mis alquileres» (nav `Header.tsx:58-61`, Home `HomePage.tsx:71`) y **puede alquilar** (`RentalsController.Create` exige policy `rentals.create`).
- Resultado esperado: el admin **no** ve «Mis alquileres», **no** puede alquilar (ni por UI ni por API), y conserva la gestión de catálogo, alquileres, solicitudes, roles y notificaciones.
- Como la BD ya existente tiene esos claims sembrados, el seed de roles debe volverse **autoritativo** (reconciliar): añade los claims del manifiesto y **elimina** los claims de tipo `permission` que ya no estén en el manifiesto del rol. Esto evita que un admin de una BD existente conserve privilegios revocados.

### R4 — Acción de alquilar para el usuario normal

- `CreateRentalDialog` ya existe y es completo (fecha límite 14 días por defecto, rango 0–30, submit vía `rentalsService.createRental`), pero **no está conectado en ninguna página** (solo se referencia a sí mismo).
- `CatalogPage` renderiza `BookCard` sin la prop `action`, por lo que el usuario normal no tiene forma de alquilar desde el catálogo.
- Resultado esperado: en `CatalogPage`, cada libro **disponible** (`book.isAvailable`) muestra un botón «Alquilar» (solo si el usuario autenticado tiene el permiso `rentals.create`), que abre `CreateRentalDialog`; al crearse el alquiler se recarga el catálogo para reflejar el stock. El admin (tras R3) no tiene `rentals.create`, por lo que no ve el botón.

### R5 — Chatbot minimizado por defecto

- `ChatWidget` se renderiza siempre expandido (`ChatWidget.tsx`). El store `chatWidgetStore` solo persiste `size` (`compact`/`large`) y dimensiones; no existe estado abierto/cerrado, por lo que la ventana siempre ocupa espacio.
- Resultado esperado: el chatbot arranca **minimizado/cerrado** (solo se ve un botón flotante «Asistente de la Biblioteca» abajo a la derecha). Al hacer clic se **maximiza/abre** la ventana, que conserva las acciones actuales (redimensionar, colapsar a compacto, teclado accesible). Al minimizar, vuelve al botón flotante.

## Technical Plan

### D1. Decisiones técnicas (Technical Lead)

1. **Configuración fail-fast (extensión ADR-016):** toda variable de configuración se lee por entorno con `GetRequiredString`/`GetRequiredInt` (backend), `import.meta.env.*` sin fallback (frontend), `os.environ` con validación explícita (Python). Si falta una variable requerida, el proceso aborta con un mensaje claro que nombra la variable. `docker-compose.yml` usa `:?` (sin `:-`).
2. **Seed de roles autoritativo:** `SeedRolesAsync` pasa de solo-añadir a **reconciliar**: por cada rol, añade los claims de su manifiesto y elimina los claims de tipo `permission` que ya no estén en el manifiesto. Garantiza que las BDs existentes pierdan `rentals.create`/`rentals.view_own` del Admin.
3. **Acción de alquilar = componente existente:** se reutiliza `CreateRentalDialog` (no se crea uno nuevo). La condición de UI es `user.permissions.includes('rentals.create') && book.isAvailable`. La seguridad la garantiza el backend (policy `rentals.create` en `RentalsController.Create`, ya existente).
4. **Chatbot minimizado = estado `isOpen` en el store:** se añade `isOpen` a `chatWidgetStore` (por defecto `false`, no persistido → siempre arranca minimizado). `ChatWidget` renderiza un botón flotante cuando está cerrado y la ventana cuando está abierto. Se conservan `size`/`widthPx`/`heightPx` persistidos.
5. **README raíz = índice:** el detalle técnico migra a READMEs por módulo (`workflow/backend/README.md`, `workflow/mcp/README.md`, y se depuran `frontend`/`chatbot`). La raíz conserva: descripción, arquitectura, flujo AI Engineering, guía de comandos, stack, estructura, quick start y enlaces.
6. **Sin cambios de contratos de API ni de esquema:** esta historia no altera endpoints, entidades ni el flujo del grafo del chatbot. Solo configuración, documentación y UX.
