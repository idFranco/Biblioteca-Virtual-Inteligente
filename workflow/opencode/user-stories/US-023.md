# User Story — US-023 — Validar al arrancar bajo docker compose que el modelo local Ollama esté activo, que exista conexión a GROQ y exponerlo en healthcheck

*(Possible statuses: Draft, Planned, Approved, In Progress, Implemented, Validated, Rejected)*

## User Story

Como administrador del proyecto, quiero que al ejecutar docker compose up --build el contenedor del chatbot valide antes de servir (fail-fast) que el modelo local Ollama esté activo en OLLAMA_BASE_URL con OLLAMA_MODEL cargado y que la conexión a GROQ (API_KEY_GROQ + GROQ_MODEL) responda, y que además el servicio declare un healthcheck (dependencias en /health, 503 degradado y unhealthy en docker compose ps si caen en runtime), para que el stack falle de forma inmediata y con diagnóstico claro cuando falte el modelo local o haya un problema de conexión a GROQ, y para poder monitorizar el estado real de ambas dependencias después del despliegue.

---

## Functional Description

Actualmente `docker compose up --build` levanta el chatbot aunque el modelo local Ollama esté apagado o GROQ esté inaccesible: el chatbot arranca y degrada silenciosamente a respuestas heurísticas (ADR-023), y el Security-Audit-MCP falla recién en la primera auditoría en runtime. El usuario no recibe ninguna señal temprana de que el stack está funcionando sin sus dependencias LLM.

Esta historia añade una **validación de arranque fail-fast** en el contenedor del chatbot y un **healthcheck de dependencias**:

1. **Validación de arranque (fail-fast):** antes de que `uvicorn` comience a servir, un módulo ejecutable (`python -m app.startup_checks`) verifica que (a) Ollama esté activo y el modelo configurado esté cargado, y (b) GROQ responda con la clave configurada. Si cualquiera falla, el proceso sale con código distinto de cero y un diagnóstico claro → `docker compose up --build` falla explícitamente.
2. **`/health` con dependencias reales:** el endpoint deja de responder un estado fijo y reporta `ollama` y `groq` con su estado actual (`200 healthy` / `503 degraded`), con una caché TTL para no martillar GROQ en cada sondeo.
3. **Healthcheck en docker-compose:** el servicio `chatbot` declara un `healthcheck` que consume `/health` (`docker compose ps` muestra `healthy`/`unhealthy` según dependencias, incluso si caen después del arranque).

Restricciones:
- La validación **no** puede ejecutarse en la fase *build* de docker (red/build sin acceso a `host.docker.internal` ni secretos en build): ocurre en el arranque del contenedor, inmediatamente después del build, que es lo que el usuario observa en `docker compose up --build`.
- No se añaden variables de entorno obligatorias nuevas: se reutilizan `OLLAMA_BASE_URL` y `OLLAMA_MODEL` (ya fail-fast si faltan, ADR-025) y `API_KEY_GROQ`/`GROQ_MODEL`/`GROQ_TIMEOUT_SECONDS` (ya exigidas en compose con `:?`).
- La degradación heurística de ADR-023 se conserva **en runtime** (si una dependencia cae estando el stack arriba, el chatbot sigue sirviendo y `/health` lo marca `degraded`); solo el **arranque** bajo compose pasa a fail-fast. Se documenta esta matización en el README/ADR.

## Acceptance Criteria

```gherkin
Feature: El stack docker compose valida el modelo local Ollama y la conexión a GROQ al arrancar y los expone en un healthcheck

  Scenario: Stack sano — arranca y el chatbot queda healthy
    Given Ollama activo en OLLAMA_BASE_URL con OLLAMA_MODEL cargado
    And GROQ responde correctamente con API_KEY_GROQ
    When ejecuto `docker compose up --build`
    Then el contenedor del chatbot arranca y sirve
    And `docker compose ps` muestra el chatbot como healthy
    And `GET /health` responde 200 con {"status":"healthy","ollama":"ok","groq":"ok"}

  Scenario: Modelo local inactivo al arrancar → falla con diagnóstico claro
    Given Ollama apagado (OLLAMA_BASE_URL inalcanzable)
    Or el modelo OLLAMA_MODEL no está cargado en Ollama
    When ejecuto `docker compose up --build`
    Then el contenedor del chatbot sale con exit code ≠ 0 antes de servir
    And el log indica que el modelo local no está activo (Ollama inalcanzable o modelo no cargado)

  Scenario: GROQ sin conexión o clave inválida al arrancar → falla con diagnóstico claro
    Given GROQ inaccesible (fallo de red)
    Or API_KEY_GROQ inválida (401/403)
    When ejecuto `docker compose up --build`
    Then el contenedor del chatbot sale con exit code ≠ 0 antes de servir
    And el log indica que no hay conexión a GROQ o la clave es inválida

  Scenario: Dependencia cae en runtime → /health degradado y contenedor unhealthy
    Given el stack está arriba con el chatbot healthy
    When Ollama o GROQ se vuelve inaccesible después del arranque
    Then `GET /health` responde 503 con {"status":"degraded", ...}
    And `docker compose ps` muestra el chatbot como unhealthy
    And el chatbot sigue respondiendo con el fallback heurístico (sin caer)

  Scenario: Regresión — tests del chatbot siguen verdes
    Given el código de validación y healthcheck está integrado
    When ejecuto `python -m pytest tests` en workflow/chatbot
    Then todos los tests pasan (nuevos de startup_checks/healthcheck + existentes)
```

## Technical Plan

### 1. Nuevo módulo `workflow/chatbot/app/startup_checks.py`

Módulo ejecutable (`python -m app.startup_checks`) y reutilizable, con funciones `async` de chequeo y helper síncrono de arranque:

- `check_ollama()`:
  - Lee `OLLAMA_BASE_URL` (fail-fast si falta) y `OLLAMA_MODEL` (fail-fast si falta).
  - `GET {OLLAMA_BASE_URL}/models` (endpoint OpenAI-compatible de Ollama; la URL ya incluye `/v1`) con `httpx.AsyncClient(timeout=...)`.
  - Éxito si el JSON contiene el `id == OLLAMA_MODEL` en la lista de modelos.
  - Fallo → `RuntimeError` con mensaje claro (host inalcanzable / conexión rechazada / modelo no cargado).
- `check_groq()`:
  - Lee `API_KEY_GROQ` (sin solución de fallback ni secreto en logs) y `GROQ_MODEL`/`GROQ_TIMEOUT_SECONDS`.
  - `GET https://api.groq.com/openai/v1/models` con `Authorization: Bearer {API_KEY_GROQ}`, timeout `GROQ_TIMEOUT_SECONDS`.
  - Éxito si `response.status_code == 200`.
  - Fallo → `RuntimeError` con diagnóstico distinto para 401/403 (clave inválida) vs fallo de red/timeout (sin conexión).
- `probe_health()`: versión ligera para `/health` con **caché TTL** (p. ej. reutiliza resultado ≤ 30s) y timeouts cortos, para no añadir latencia ni martillar GROQ en cada sondeo. Devuelve `{"ollama": "ok"|"down"|"error", "groq": ...}` sin lanzar excepciones.
- Entrada `if __name__ == "__main__":` → ejecuta los dos checks, imprime `[startup-checks] OK` o el diagnóstico de error en `stderr`, y `sys.exit(0)` / `sys.exit(1)`.

### 2. `workflow/chatbot/Dockerfile`

Cambiar el `CMD` para que el arranque valide antes de servir (`&&` mantiene el parámetro `exec` final):

```dockerfile
CMD ["sh", "-c", "python -m app.startup_checks && exec uvicorn main:app --host \"$HOST\" --port \"$PORT\""]
```

- Falla → `exit 1`, log con diagnóstico visible en `docker compose logs chatbot`.
- No se necesitan más cambios: `python` y `httpx` ya están en la imagen (`requirements.txt`).

### 3. `/health` con dependencias reales (`workflow/chatbot/main.py`)

- `GET /health` → usa `probe_health()` con caché TTL.
  - Todo OK → `200 {"status": "healthy", "ollama": "ok", "groq": "ok"}`
  - Cualquier dependencia caída → `503 {"status": "degraded", "ollama": "down", "groq": "..."}`
- Mantiene retrocompatibilidad de contrato (el frontend no consume `/health`; lo usa el healthcheck de compose).

### 4. Healthcheck en `docker-compose.yml` (servicio `chatbot`)

```yaml
healthcheck:
  test: ["CMD", "python", "-m", "app.healthcheck"]
  interval: 30s
  timeout: 10s
  retries: 3
  start_period: 30s
```

- `app.healthcheck.py`: script síncrono que hace `GET http://127.0.0.1:8000/health` con `urllib.request` (la imagen `python:3.12-slim` no trae `curl`); `exit 0` si 200, `exit 1` si 503 o error.
- `docker compose ps` pasa a `healthy`/`unhealthy` según el estado real de Ollama+GROQ.

### 5. Tests (`workflow/chatbot/tests/`)

- `test_startup_checks.py`: hermético (sin red), mockeando `httpx` (o `monkeypatch` del cliente):
  - `check_ollama()` OK (modelo presente en la lista).
  - `check_ollama()` host inalcanzable → `RuntimeError` con diagnóstico.
  - `check_ollama()` modelo no cargado → `RuntimeError`.
  - `check_groq()` OK (200).
  - `check_groq()` 401/403 → `RuntimeError` de clave inválida.
  - `check_groq()` timeout/network → `RuntimeError` de sin conexión.
  - `probe_health()` devuelve mapa ok/down/error sin lanzar; TTL evita llamadas repetidas.
- `test_health.py` (o extensión): `/health` sano → 200 + campos `ollama`/`groq`; uno caído → 503 `degraded`.
- El job `python` de `ci.yml` corre `python -m pytest tests` en `workflow/chatbot`, por lo que los nuevos tests entran al pipeline sin cambios en el workflow.

### 6. Documentación y limpieza

- README `workflow/chatbot`: mover/reemplazar el bloque o la línea de `GET /health` y añadir sección "Validación de arranque y healthcheck" (comportamiento fail-fast, semántica de `/health`, healthcheck de compose).
- Matización ADR: se registra en la bitácora que el arranque bajo compose es fail-fast sobre Ollama/GROQ (manteniendo degradación ADR-023 en runtime).
- Sin cambios en `.env.example` salvo comentario si aplica (no se añaden variables nuevas).
