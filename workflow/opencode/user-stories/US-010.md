# User Story — US-010 — Persistir datos de ejemplo y aplicar identidad visual de librería

*(Possible statuses: Draft, Planned, Approved, In Progress, Implemented, Validated, Rejected)*

## User Story

Como administrador del proyecto, quiero que se persistan datos de ejemplo en la base de datos (alrededor de 50 libros de diferentes géneros) y verificar su disponibilidad en Open Library; y como usuario, quiero que la vista de la aplicación de alquiler de libros tenga una identidad visual acorde a una librería (colores cálidos y añejos, estética de librería tradicional), para que la experiencia de navegación sea coherente con el propósito del sistema.

---

## Functional Description

La historia tiene dos partes independientes pero complementarias: **(A) persistir ~50 libros de ejemplo y verificar su disponibilidad en Open Library** y **(B) aplicar una identidad visual de librería tradicional** a la aplicación.

### Parte A — Seed de catálogo (~50 libros) + verificación en Open Library

1. **Seed idempotente de libros de ejemplo.** Al arrancar el backend (tras `EnsureCreated`, el seed de roles y el de administrador ya existentes en `Program.cs`), se persisten ~50 libros de ejemplo (obras reales, mayormente clásicos de dominio público) con los campos del modelo `Book` actual: `Title`, `Author`, `Isbn`, `Genre`, `Description`, `OpenLibraryKey`, `TotalCopies` y `AvailableCopies`. El seed debe ser idempotente con el mismo patrón de `SeedRolesAsync`/`SeedAdministratorAsync`: si la tabla `Books` ya contiene registros, **no** se duplica nada.
2. **Diversidad de géneros.** Los ~50 libros deben cubrir al menos 8 géneros distintos (p. ej. Novela, Ciencia Ficción, Fantasía, Misterio/Thriller, Historia, Biografía, Poesía, Ensayo, Clásicos, Aventura) para que el filtro por género y la búsqueda del catálogo (UC-5) tengan resultados significativos y demostrables.
3. **Variación de disponibilidad de copias.** Los libros deben tener `TotalCopies` entre 1 y 5, con `AvailableCopies = TotalCopies` en la mayoría, y **al menos un libro con 0 copias disponibles** para ejercitar el filtro "Solo disponibles" y el badge de disponibilidad (UC-5, UC-7).
4. **Verificación de disponibilidad en Open Library.** Cada libro del seed debe corresponder a una obra real indexada en Open Library, con su `OpenLibraryKey` válido. La verificación se realiza consultando el MCP de Open Library (`ol_search_books` por ISBN/título y/o `ol_get_book_details` con la clave — tools ya existentes, servidor ya activo tras US-009 según ADR-014) y confirmando que cada obra existe y el título coincide. Esta verificación es un **paso de validación de datos del seed** (lo ejecuta el equipo de QA/desarrollo contra el MCP), **no** una funcionalidad en runtime: conforme a ADR-007, el frontend no invoca MCP directamente y la app no consulta Open Library en cada visita.

### Parte B — Identidad visual de librería (colores cálidos y añejos)

1. **Tema global de librería tradicional.** La SPA adopta una paleta de librería clásica: fondos crema/pergamino, marrones cálidos (madera, cuero), acentos ámbar/dorado y verde musgo/botella, con texto en marrones oscuros de alto contraste. La paleta se redefine en los tokens de tema de `src/index.css` (`@theme` / `:root` / `.dark`), conservando la arquitectura de CSS variables de shadcn/ui (baseColor `neutral` actual → paleta cálida).
2. **Componentes de layout.** `Header` y `Footer` reciben la identidad (fondo marrón/madera oscura, texto crema, enlaces con hover ámbar), manteniendo intactos la navegación, el nombre "Biblioteca Virtual" (estilizado acorde) y los enlaces condicionados por permisos (UC-4).
3. **Sustitución de colores hardcodeados.** Las clases de color genéricas actuales (`gray-*`, `blue-600`, `red-600`, `green-100/800`, `red-100/800`, `blue-100/800`, `bg-white`, etc. — presentes en Header, Footer, CatalogPage, BooksAdminPage, MisAlquileresPage, AlquileresAdminPage, GestionLibroPage, LoginPage, RegisterPage, CreateRentalDialog, RequestStatusBadge y ChatWidget) se sustituyen por la paleta temática, incluyendo botones primarios, inputs/bordes, tablas, diálogos y badges de estado (disponibilidad, alquiler, solicitudes).
4. **Sin cambio funcional.** La identidad visual no altera rutas, guardias de permisos, lógica de negocio ni contratos de API; es un cambio exclusivamente de presentación coherente con el propósito del sistema.

## AI/MCP Plan (AI Engineer)

### 1. Contexto de la integración Open Library existente (de US-009)

- El proyecto usa **servidor MCP externo propio** (`workflow/mcp/open-library-mcp/server.py`, FastMCP + httpx contra `https://openlibrary.org`) con dos tools ya validadas: `ol_search_books(query, limit)` (búsqueda por título/autor/ISBN) y `ol_get_book_details(key)` (detalle por OLID). US-009 quedó **Validated** y el servidor ya está activo (ADR-014).
- El chatbot consume ese MCP por stdio vía `workflow/chatbot/app/mcp_clients/open_library_client.py` → `stdio.py` (`run_mcp_tool`), con fallback Bug 2 en `external_enrichment_node` (Open Library caído → respuesta amable, sin colapso).
- **No existe** hoy un mecanismo de verificación masiva por ISBN (el endpoint `/api/books?bibkeys=ISBN:...` de Open Library no está expuesto). Para US-010 hace falta una verificación **por ISBN exacto** de ~50 libros.

### 2. Enfoque de verificación de disponibilidad en Open Library

- **Cómo se consulta:** por **ISBN exacto** (identificador inequívoco), con respaldo por título+autor si el ISBN no resuelve. No se usan OpenLibraryKey de entrada (precisamente se quiere *obtener*/validar la key de cada obra).
- **Dónde se ejecuta:** script **one-off de desarrollo/QA** (`workflow/scripts/verify_seed_open_library.py`), NO un endpoint del backend (ADR-007: la app no consulta Open Library en runtime) NI una task del chatbot. El script invoca el MCP por stdio reutilizando `McpStdioClient` (mismo patrón que el chatbot) → cero duplicación de clientes HTTP.
- **Formato de salida:** `workflow/database/openlibrary_verification.json` con una entrada por libro: `title`, `author`, `isbn`, `found` (bool), `open_library_key` (OLID o null), `matched_title` (título devuelto por OL para validar coincidencia), `strategy` (`isbn` | `title_author` | `not_found`), `verified_at` (UTC). Resumen final: `{ total: 50, found: 50, not_found: 0 }`. Criterio de aceptación: **100% de los libros confirmados** — si alguno no se confirma, se corrige el ISBN/título en el dataset del seed (nunca se siembra una key falsa ni se marca como encontrado sin coincidencia).
- **Qué se considera "disponible":** la obra existe en Open Library y el título devuelto coincide con el sembrado (comparación normalizada, sin acentos y case-insensitive). No se usa el campo de préstamo/biblioteca de OL (irrelevante para el sistema interno).
- **Sin cambios en el grafo:** el chatbot no necesita modificaciones para US-010; `external_enrichment_node` ya enriquece y `availability_node` ya compone ofertas. El seed solo aporta datos reales al catálogo interno que lee `Biblioteca-MCP`.

### 3. Cambios en el servidor Open Library MCP

- **Nueva tool `ol_verify_by_isbn(isbn)`** (ampliación mínima, respetando mcp-rules: schema claro, errores estructurados, sin secretos):
  - `GET /api/books?bibkeys=ISBN:{isbn}&format=json&jscmd=data` → si el ISBN existe, devuelve la key (OLID) de la obra; si no, `{}`/empty.
  - Respuesta: `{ "isbn": ..., "found": bool, "open_library_key": OLID | null, "title": ... }` (con `jscmd=data` se obtiene el título para validar coincidencia).
  - Fallback interno: si `/api/books` falla (timeout/HTTPError), el script cae a `ol_search_books(isbn)` → top-1 con validación de coincidencia (mismo criterio de Bug 2 del chatbot).
- **Tests:** se añade cobertura pytest para la tool (con `httpx.MockTransport`): ISBN existente, ISBN inexistente, timeout → error estructurado, validación de schema.

### 6. Riesgos de integración y mitigación

| Riesgo | Nivel | Mitigación |
|---|---|---|
| Rate limiting de Open Library (~100 req/min sin API key; límites no documentados) | Medio | El script serializa las llamadas con sleep ≥ 1s entre ISBNs (~50 llamadas ≈ 1 min de margen), reintento con backoff exponencial (2 intentos), y `OPEN_LIBRARY_SEARCH_LIMIT`/timeout configurables por env. |
| Errores de red / timeouts (10s por defecto) | Medio | Timeout configurable (`OPEN_LIBRARY_TIMEOUT`), reintentos, y fallback a `ol_search_books` cuando `/api/books` no responde. |
| ISBN no encontrado en Open Library (obras sin edición con ISBN indexado) | Medio | Respaldo por título+autor normalizado; si aún no se confirma, el libro se marca `not_found` y se **corrige el dataset** (cambiar ISBN/obra) — jamás se siembra una key inventada. QA valida 100% de confirmación. |
| Homónimos / coincidencia de título incorrecta | Alto | Validación de coincidencia normalizada (título devuelto vs. sembrado); si difiere, `found: false` con el título real para decisión humana. |
| Dependencia de red para validar el seed | Bajo | La verificación es un paso de datos de desarrollo/QA; la app en runtime no depende de Open Library (ADR-007). |
| Regeneración de BD por `EnsureCreated` | Bajo | El seed corre tras `EnsureCreated` cada arranque pero es idempotente (solo si `Books` vacía), mismo patrón que roles/admin. |
