# User Story — US-018 — Corregir arranque de MCP en contenedor y resiliencia de Open Library

*(Possible statuses: Draft, Planned, Approved, In Progress, Implemented, Validated, Rejected)*

## User Story

Como administrador del proyecto, quiero que el arranque del stack bajo docker compose resuelva las variables de rutas de base de datos (DATABASE_PATH, AUDIT_DATABASE_PATH) exclusivamente desde el archivo .env mediante env_file en Docker Compose, para que los exports del shell del host (precedencia shell > .env) no rompan los servidores MCP internos con FileNotFoundError; y que open-library-mcp tolere fallos transitorios de red (ConnectError tras el build) mediante reintento con backoff y timeout ampliado, para que docker compose up --build funcione sin errores y el chatbot responda correctamente al interactuar desde la página.

---

## Functional Description

El log de `docker compose up --build` (`~/Documents/dev/problems.txt`) muestra dos fallas al interactuar con el chatbot desde la página:

1. **`biblioteca-mcp` y `security-audit-mcp` crashean al arrancar** con `FileNotFoundError: El directorio de la base de datos no existe: /app/workflow/database … DATABASE_PATH (actual: './workflow/database/BibliotecaVirtual.db')`. Causa raíz verificada empíricamente: el shell del host exporta `DATABASE_PATH=./workflow/database/BibliotecaVirtual.db` (desde `~/.bashrc:142`, legítimo para dev en host), y Docker Compose resuelve la sustitución `${DATABASE_PATH}` de `environment:` con **precedencia shell > `.env`**. El contenedor recibe la ruta relativa, que `get_database_path` resuelve contra `/app` → `/app/workflow/database` (inexistente; el volumen vive en `/app/database`). El `.env` ya contiene el valor correcto (`/app/database/BibliotecaVirtual.db`), pero es sombreado por el shell.
2. **`open-library-mcp` falla con `ConnectError` transitorio** en `ol_search_books` justo tras el build (host con egres OK: HTTP 200, DNS OK, sin proxy). El nodo `external_enrichment_node` ya lo degrada sin colapsar, pero un solo intento con timeout de 10 s es frágil ante blips de DNS/red post-build.

### Comportamiento esperado

1. **Arranque gobernado por `.env`.** Las rutas de BD llegan al contenedor desde el archivo `.env` del disco vía `env_file` (que NO consulta el entorno del shell), por lo que ningún export del host puede sombrearlas. El resto de las variables (`OLLAMA_*`, `CORS_ORIGINS`, `API_KEY_GROQ`, comandos MCP) sigue resolviéndose por sustitución desde `.env` (el shell no las exporta).
2. **Sin cambios en el shell del host.** El export de `~/.bashrc` se conserva para dev fuera de Docker; deja de afectar al contenedor.
3. **Open Library resiliente.** `_get_json` reintenta errores de transporte (`ConnectError`, timeouts) con backoff breve; el timeout por intento sube de 10 s a ~12 s manteniendo el peor caso total por debajo del cap externo de 30 s de `run_mcp_tool`. Si aun así falla, el grafo continúa con `enrichment_error=True` (comportamiento existente preservado).
4. **Cero cambios funcionales de negocio.** Sin cambios en grafo, nodos, auditoría, PII masking ni catálogo.

```gherkin

  When ejecuto docker compose up --build -d

  And los servidores biblioteca-mcp y security-audit-mcp inician por stdio sin traceback

  And DATABASE_PATH=./workflow/database/BibliotecaVirtual.db exportada en el shell del host
  When inspecciono printenv dentro del contenedor chatbot
  Then DATABASE_PATH es /app/database/BibliotecaVirtual.db (valor del .env, ignorando el shell)
  And AUDIT_DATABASE_PATH es /app/database/audit.db

Scenario: Chatbot funcional desde la página tras el arranque
  Given el stack levantado según el escenario 1
  When el usuario envía un mensaje vía POST /chat desde la SPA
  Then la respuesta es HTTP 200 procesada por el grafo completo (auditoría input incluida)

Scenario: Open Library tolera fallo transitorio de red
  Given openlibrary.org momentáneamente inalcanzable desde el contenedor
  When una consulta book_query dispara ol_search_books
  Then se ejecuta el reintento con backoff sobre el error de transporte
  And si persiste el fallo, external_enrichment marca enrichment_error y el chat responde 200 sin colapsar
```

## Technical Plan

### 1. `docker-compose.yml` — servicio `chatbot`
- Eliminar de `environment:` las líneas:
  ```yaml
      - DATABASE_PATH=${DATABASE_PATH:?Set DATABASE_PATH in the .env file (e.g. /app/database/BibliotecaVirtual.db)}
      - AUDIT_DATABASE_PATH=${AUDIT_DATABASE_PATH:?Set AUDIT_DATABASE_PATH in the .env file (e.g. /app/database/audit.db)}
  ```
- Añadir después del bloque `environment:`:
  ```yaml
      env_file:
        - .env
  ```
- Justificación: `env_file` lee el archivo del disco al construir el entorno del contenedor y **no** aplica precedencia del shell; las claves ausentes en `environment:` pasan tal cual desde `.env`. Las claves que permanecen en `environment:` siguen teniendo prioridad (comportamiento estándar Compose).
- Servicio `backend`: **sin cambios** (ya resuelve `SQLITE_DATA_SOURCE` desde `.env`; el shell no lo exporta). Queda como mejora futura opcional.

### 2. `workflow/mcp/open-library-mcp/server.py`
- Nuevo módulo-env: `OPEN_LIBRARY_RETRIES = int(os.getenv("OPEN_LIBRARY_RETRIES", "1"))` (reintentos extra; consistente con el estilo existente de `OPEN_LIBRARY_BASE_URL`/`OPEN_LIBRARY_TIMEOUT`).
- `OPEN_LIBRARY_TIMEOUT` default `10` → `12`.
- `_get_json`: bucle de hasta `1 + OPEN_LIBRARY_RETRIES` intentos; reintenta únicamente sobre `httpx.TransportError` (incluye `ConnectError` y timeouts) con backoff fijo ~1 s entre intentos; otros `httpx.HTTPError` (4xx/5xx) fallan sin reintento; el error final mantiene el `RuntimeError("Open Library no respondió…")` actual.
- Presupuesto de peor caso: 2 intentos × 12 s + 1 s backoff ≈ 25 s < cap de 30 s de `asyncio.wait_for` en `run_mcp_tool`.

### 3. Tests
- `workflow/mcp/open-library-mcp/tests/`: test unitario del reintento con cliente httpx simulado (monkeypatch) que falla la primera llamada con `ConnectError` y pasa en la segunda; test de no-reintento para `HTTPStatusError`. Sin red real.

### 4. Documentación
- `.env.example`: retirar el comentario-workaround (líneas ~40-41: «si exportas DATABASE_PATH relativa… pásale el valor in-image a compose») y reemplazar por la explicación del mecanismo `env_file`.
- `.opencode/memory/DECISIONS.md`: **ADR-033** (arranque de contenedor gobernado por `.env` vía `env_file`; matiz a ADR-025: se pierde el `:?` de compose para esas 2 claves, mitigado por `require_env`/`get_database_path` fail-fast en los MCP; trade-off aceptado de inyectar todo `.env` al chatbot). Mirror en `codebase-memory_manage_adr`.
- README raíz / README chatbot: sin cambios requeridos (la guía de arranque sigue válida).

### Sin cambios
- `~/.bashrc` del host, código Python/C#/React de negocio, grafo LangGraph, nodos de auditoría, PII masking, Dockerfiles, CI.
