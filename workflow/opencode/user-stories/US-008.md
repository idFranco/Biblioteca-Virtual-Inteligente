# User Story — US-008 — Limpieza de código, variables de entorno en Docker, actualización de imágenes Docker e integración de .env.example

*(Possible statuses: Draft, Planned, Approved, In Progress, Implemented, Validated, Rejected)*

## User Story

Como administrador del proyecto, quiero realizar una limpieza general del código creando métodos de extensión donde la detección lo requiera para mejor legibilidad, validar que todas las variables de entorno declaradas sean efectivamente utilizadas tanto en las aplicaciones como en los archivos Docker, manejar Docker exclusivamente mediante variables de entorno (informando al usuario cuando existan contenedores/instancias previas para que las recree), asegurar que si se construye una imagen Docker se actualice la existente en lugar de crear nuevas, e integrar el archivo `.env.example` en el repositorio documentándolo en el `README.md` principal de la raíz del proyecto, para reducir la deuda técnica y mantener la coherencia del stack.

---

## Functional Description

La US-008 es una historia de remediación transversal de deuda técnica (sin nuevas funcionalidades de negocio) cuyo objetivo es dejar el repositorio del proyecto limpio, coherente y reproducible.

1. **Limpieza de código con métodos de extensión/helpers**: se extraen los patrones repetidos de lectura de configuración (backend C#, frontend TypeScript, Python MCP) a métodos de extensión o módulos helpers centralizados, con la condición estricta de no alterar el comportamiento funcional de ningún módulo.
2. **Auditoría bidireccional de variables de entorno**: toda variable declarada (en `appsettings.json`, `.env.example`, `docker-compose.yml`, `Dockerfiles`, `opencode.json`) debe tener un consumo efectivo en código, y toda variable consumida debe estar declarada o validada con un mensaje de error claro al arrancar.
3. **Docker exclusivamente mediante variables de entorno**: se eliminan valores hardcodeados del `docker-compose.yml` (entornos, connection strings) parametrizándolos vía interpolación `${VAR}` desde el `.env` raíz; el flujo documentado debe informar al usuario cuando existan contenedores/imágenes previas para que los recree.
4. **Actualización de imágenes Docker (mismo tag)**: se definen tags de imagen estables para que construir una imagen actualice la existente en lugar de crear nuevas imágenes/tags.
5. **Integración y documentación de `.env.example`**: el archivo queda versionado en Git (el `.gitignore` solo excluye `.env`, `.env.local`, `.env.*.local`) con todas las variables del stack y se documenta en el `README.md` principal de la raíz (sección 6.1) con lista completa de variables, requerida/opcional, valor por defecto y consumidor.

Tras la remediación, los 10 casos de uso core deben seguir funcionando de forma idéntica. El chatbot actual es un stub (solo `/health`): se audita que no declare variables sin uso; las variables del LLM se declaran como opcionales/futuras en `.env.example`, sin cablearlas todavía.

## Acceptance Criteria

```gherkin
# Requisito (a) — Limpieza de código con métodos de extensión, sin cambio de comportamiento
Scenario: Refactor con métodos de extensión sin alterar comportamiento
  Given un módulo del stack (backend, frontend o MCP) con lógica repetida o poco legible candidata a extracción
  When se refactoriza creando métodos de extensión o helpers en los puntos detectados
  Then la legibilidad mejora sin cambiar el comportamiento funcional del módulo
  And la build del módulo compila sin errores (dotnet build / npm run build)
  And el refactor no introduce TODOs, stubs, ni valores mock/hardcodeados nuevos

# Requisito (b) — Toda variable de entorno declarada es efectivamente utilizada/validada (aplicaciones + Docker)
Scenario: Auditoría bidireccional de variables de entorno
  Given el inventario de variables declaradas por cada módulo (backend: JWT_KEY, ADMIN_EMAIL, ADMIN_PASSWORD, AUTH_RATE_LIMIT_PER_MINUTE, SQLITE_DATA_SOURCE; frontend: VITE_API_BASE_URL; MCPs: DATABASE_PATH)
  When se audita cada variable contra su consumo real en el código y en los archivos Docker
  Then toda variable declarada tiene un punto de consumo efectivo y documentado
  And toda variable consumida está declarada en .env.example con su valor por defecto o placeholder
  And si una variable obligatoria falta al arrancar, la aplicación falla con un mensaje de error claro que nombra la variable (no falla silenciosa ni con secretos literales)
  And docker compose up --build levanta backend, frontend y chatbot leyendo exclusivamente las variables del .env raíz

# Requisito (c) — Docker exclusivamente con variables de entorno + aviso de instancias previas
Scenario: Configuración Docker 100% por variables de entorno
  Given el usuario ejecuta el flujo Docker documentado
  When el compose inicia los servicios
  Then todas las opciones de entorno y configuración de los servicios provienen de variables de entorno
  And la documentación indica el procedimiento para crear el .env a partir de .env.example

Scenario: Aviso informativo cuando existen contenedores/imágenes previas
  Given que existen contenedores o imágenes previas del stack en el host
  When el usuario inicia el flujo Docker documentado (docker compose up --build)
  Then la documentación informa explícitamente que existen instancias previas
  And se indica recrear los contenedores (docker compose down + docker compose up --build) para aplicar la nueva configuración

# Requisito (d) — Construir una imagen Docker actualiza la existente
Scenario: Build Docker con tag estable que actualiza la imagen existente
  Given que ya existe una imagen Docker del servicio con un tag estable
  When se ejecuta nuevamente el build
  Then la imagen con el mismo tag se actualiza/sobrescribe en lugar de crear imágenes nuevas con tags distintos
  And el inventario local de imágenes no acumula versiones huérfanas por cada build
  And la referencia usada por docker compose apunta siempre al mismo tag estable

# Requisito (e) — .env.example integrado y documentado en README.md de la raíz
Scenario: Integración y documentación de .env.example
  Given el repositorio raíz del proyecto
  When se integra .env.example con TODAS las variables del stack
  Then .env.example está versionado en Git (no excluido por .gitignore)
  And .env.example no contiene secretos reales, solo placeholders
  And el README.md principal documenta .env.example: propósito, lista completa de variables con descripción, y el comando cp .env.example .env
  And las constantes documentadas quedan alineadas (sin divergencias de valores como Biblioteca.db vs BibliotecaVirtual.db ni de puertos 8000 vs 8001)
```

## Technical Plan

División estricta refactor (sin cambio de comportamiento) vs. comportamiento (inyección/infraestructura).

**A. Backend (refactor + hardening)**
1. Nuevo `workflow/backend/src/Infrastructure/Common/ConfigurationExtensions.cs` (namespace `BibliotecaVirtual.Infrastructure.Common`):
   - `GetRequiredString(this IConfiguration, string key)` — lanza `InvalidOperationException` nombrando la variable si es null/whitespace. Reemplaza el patrón duplicado `config["Jwt:Key"] ?? throw ...` en `Program.cs:40-41` y `TokenService.cs:80-81`.
   - `GetString(this IConfiguration, string key, string defaultValue)` — unifica los 4 reads de `Jwt:Issuer`/`Jwt:Audience`.
   - `GetInt(this IConfiguration, string key, int defaultValue)` — unifica `Jwt:AccessTokenExpirationMinutes` (leído 2× en `TokenService.cs:40,84`), `Jwt:RefreshTokenExpirationDays`, `AUTH_RATE_LIMIT_PER_MINUTE`.
   - Restricción de capas: vive en **Infrastructure** (única asamblea compartible entre `TokenService` y `Program.cs`); nunca en WebAPI.
2. Aplicar los helpers en `Program.cs` y `TokenService.cs` preservando byte-a-byte los defaults actuales (`15`, `7`, `"BibliotecaVirtual"`, `"http://localhost:5173"`, `AUTH_RATE_LIMIT_PER_MINUTE=10`).
3. **Fix crítico placeholder JWT**: `appsettings.json` `"Key": "${JWT_KEY}"` no se expande en .NET → clave literal `${JWT_KEY}`. Retirar el literal de `appsettings.json`; dev-key solo en `appsettings.Development.json`; en `Program.cs` exigir `Jwt__Key` con fallo estricto (fail-closed) fuera de Desarrollo. Nota: rotar la clave invalida tokens previos (aceptable pre-producción; documentar re-login).
4. Opcional: crear `appsettings.Production.json` (Logging/Strict) que hoy no existe.

**B. Frontend (refactor + build-time injection)**
1. Nuevo `workflow/frontend/src/config/env.ts` exportando `API_BASE_URL = import.meta.env.VITE_API_BASE_URL ?? 'http://localhost:5000'` (default canonical acorde a docker-compose; corrige el `:5002` roto). 
2. Nuevo `workflow/frontend/src/vite-env.d.ts` con `interface ImportMetaEnv { readonly VITE_API_BASE_URL?: string }`.
3. `workflow/frontend/src/services/api.ts` y `auth.ts` importan `API_BASE_URL` desde `config/env.ts` (elimina duplicación).
4. `workflow/frontend/Dockerfile`: `ARG VITE_API_BASE_URL` + `ENV VITE_API_BASE_URL=$VITE_API_BASE_URL` antes de `npm run build`; `docker-compose.yml` `build.args: VITE_API_BASE_URL`. **Borde estricto US-008:** no tocar el runtime nginx (EXPOSE 5173 vs puerto 80 es tema de US-007/Approved).

**C. Python MCP (refactor + hardening)**
1. Nuevo `workflow/mcp/common/settings.py` (+ `__init__.py`) — solo stdlib (`os`, `pathlib`, `functools`): `get_database_path(env_name="DATABASE_PATH", default=..., base_dir=repo_root) -> Path`; tratar `""` como no definido (bug actual), resolver relativos contra repo root (corrige la ruta rota `../database/...`), validar `parent.is_dir()` con `FileNotFoundError` absoluto, `@lru_cache`, `clear_settings_cache()` para tests.
2. En ambos `server.py` (biblioteca y security-audit): bootstrap de `sys.path` → `workflow/mcp/`, `from common.settings import get_database_path`, `DATABASE_PATH = get_database_path()`.
3. Dockerfiles MCP: sin `ENV DATABASE_PATH` ni defaults baked; inyección solo en runtime (compose cuando existan servicios MCP, fuera de US-008). `opencode.json` sin cambios (ADR-014).
4. Chatbot `Dockerfile`: `CMD` env-driven `HOST`/`PORT` con defaults (`0.0.0.0`/`8000`); sin env de negocio.

**D. Docker (comportamiento)**
1. `docker-compose.yml`:
   - Backend: `environment` con `Jwt__Key: ${JWT_KEY:?JWT_KEY is required}`, `ADMIN_EMAIL: ${ADMIN_EMAIL:-}`, `ADMIN_PASSWORD: ${ADMIN_PASSWORD:-}`, `AUTH_RATE_LIMIT_PER_MINUTE: ${AUTH_RATE_LIMIT_PER_MINUTE:-10}`, `SQLITE_DATA_SOURCE: ${SQLITE_DATA_SOURCE:-}`; mantener `ASPNETCORE_ENVIRONMENT` y connection string (parametrizado desde `.env`).
   - Frontend: `build.args: VITE_API_BASE_URL: ${VITE_API_BASE_URL:-http://localhost:5000}`.
   - Chatbot: `environment` `HOST`/`PORT` opcionales (por defecto).
   - `image:` stable tags (p. ej. `biblioteca-virtual-backend:stable`, `...-frontend:stable`, `...-chatbot:stable`) — el build sobrescribe el mismo tag, nunca tags nuevos por cambio de código (política US-008 + futuro ADR-015).
2. Sin valores hardcodeados de entorno/conn strings en compose: todos vía `${VAR}` (`.env` raíz). Cero secretos reales commiteados.
3. Documentación del flujo: `cp .env.example .env`, y **aviso explícito** de que si existen contenedores/instancias previas deben recrearse (`docker compose down` + `docker compose up --build`) — requisito (c).
4. **Alcance estricto + orden de merge**: US-008 toca SOLO env passthrough/build-args/`image:` de servicios existentes; topología, puertos y nginx son de US-007 (Approved). Enforce US-007 → US-008. Si US-007 no está mergeada antes de implementar, HALT y reportar.

**E. `opencode.json`** — SIN CAMBIOS (ADR-014; wiring `DATABASE_PATH` y `GITHUB_TOKEN` ya correctos).

**F. `.env.example` + docs (integración)**
1. `.env.example` versionado (verificado: `.gitignore` solo excluye `.env`, `.env.local`, `.env.*.local`): añadir `VITE_API_BASE_URL` y placeholders comentados/futuros `LLM_API_KEY`, `LLM_API_URL`, `LLM_MODEL`, `LLM_TEMPERATURE`, `LLM_TIMEOUT_SECONDS`, `CHATBOT_CORS_ORIGINS`. Requeridas: `JWT_KEY`, `ADMIN_EMAIL`, `ADMIN_PASSWORD`, `DATABASE_PATH`, `GITHUB_TOKEN`, `VITE_API_BASE_URL`. Opcional: `AUTH_RATE_LIMIT_PER_MINUTE`. Nunca valores secretos reales.
2. README sección 6.1 → tabla completa `Variable | Requerida/Opcional | Valor default | Consumidor`, con `cp .env.example .env`. Corregir divergencias documentadas (ver Documentación Plan).

**G. Auditoría de coherencia (QA automatizable)**
- Keys `(.env.example)` vs keys usadas (grep en `src`, `opencode.json`, `docker-compose.yml`, Dockerfiles): balance 0 huérfanos en ambas direcciones; mapeo `JWT_KEY`→`Jwt__Key` verificado; `docker compose config` muestra sustitución real (no literal `${...}`).
