# User Story — US-007 — Alinear archivos Docker con las aplicaciones

*(Possible statuses: Draft, Planned, Approved, In Progress, Implemented, Validated, Rejected)*

## User Story

Como administrador del proyecto, quiero alinear los archivos Docker (Dockerfiles y docker-compose.yml) con las aplicaciones para que el stack completo funcione sin inconsistencias de puertos, variables de entorno y URL base de la API al ejecutar `docker compose up --build`.

---

## Functional Description

**Ámbito:** Trabajo de alineación de infraestructura **exclusivamente** (Dockerfiles, `docker-compose.yml`, configuración nginx y variables de entorno de despliegue). **No** se modifica ninguna regla de negocio, endpoint, contrato de API ni comportamiento de la UI. El objetivo es que `docker compose up --build` levante el stack completo (backend 5000, frontend 5173, chatbot 8000) y que los 3 módulos interoperen igual que en desarrollo local.

**Comportamiento esperado tras el fix (visible al usuario):**
- El stack arranca completo y estable: `docker compose up --build` compila las 3 imágenes sin errores y los 3 contenedores quedan running.
- La SPA es alcanzable en `http://localhost:5173`: nginx sirve la aplicación y **cualquier ruta de React Router** (p. ej. `/login`, `/libros`) responde 200 al refrescar la página (fallback SPA), no 404.
- Funcionan registro e inicio de sesión: el backend inicializa la base SQLite con roles/permisos y **siembra el usuario administrador** definido por `ADMIN_EMAIL`/`ADMIN_PASSWORD`; el login del admin devuelve token JWT válido (desaparece el 400/IDX10653 por key literal `${JWT_KEY}`).
- Las llamadas de la SPA llegan al backend: la URL base de la API embebida en el bundle apunta a `http://localhost:5000` (build arg `VITE_API_BASE_URL`), con CORS ya habilitado para `http://localhost:5173`.
- El chatbot responde a su health check en `http://localhost:8000` (sin cambios funcionales).

**Nota operativa:** el backend requiere credenciales de arranque; antes de `docker compose up` hay que crear `.env` copiando `.env.example` (ver README). Sin `.env`, `docker compose up` aborta con mensaje explícito (fail-fast intencional, política de cero secretos en el repositorio).

## Technical Plan

### Contexto validado en runtime (3 inconsistencias reales)

1. **Frontend inalcanzable:** `nginx:alpine` escucha en puerto 80 (config por defecto), pero compose mapea `5173:5173` y el Dockerfile `EXPOSE 5173` → nada escucha en 5173 → `HTTP 000` (verificado). Además, sin `try_files ... /index.html`, el refresco de rutas de React Router devuelve 404.
2. **Auth backend roto en compose:** `appsettings.json` tiene `"Jwt:Key": "${JWT_KEY}"` como **texto literal** (.NET no interpola `${VAR}`; solo Compose lo hace dentro del propio YAML). Sin `Jwt__Key`/`JWT_KEY` ni `ADMIN_EMAIL`/`ADMIN_PASSWORD` en el servicio backend → login/register fallan con 400 (IDX10653) y el seed de admin se salta silenciosamente (verificado con `docker inspect`).
3. **URL base de API desalineada:** `api.ts`/`auth.ts` usan default `http://localhost:5002` (correcto solo para dev local), pero en compose el backend se publica en `5000`; el bundle de producción debe embeber `http://localhost:5000` vía build arg.

### Decisiones técnicas consolidadas

| # | Decisión | Justificación |
|---|---|---|
| D1 | **nginx.conf propio con `listen 5173`** (Opción A). No se cambia el mapeo `5173:5173` | El SPA fallback obliga a escribir nginx.conf de todos modos; `listen 5173` mantiene un único número de puerto en todo el stack (compose/EXPOSE/CORS/README), sin tocar backend ni CORS. Se descarta `5173:80` (dos números para el mismo servicio). |
| D2 | **Env backend obligatorios**: `Jwt__Key=${JWT_KEY:?...}`, `ADMIN_EMAIL=${ADMIN_EMAIL:?...}`, `ADMIN_PASSWORD=${ADMIN_PASSWORD:?...}`; opcional `AUTH_RATE_LIMIT_PER_MINUTE=${...:-10}` | Política de cero secretos hardcodeados (AGENTS.md #8) + fail-fast: sin `.env` el compose aborta con mensaje claro en lugar de arrancar roto/inseguro. Los defaults dev (`:-`) para secretos se rechazan: quedarían commiteados. |
| D3 | **Build arg `VITE_API_BASE_URL=http://localhost:5000`** (ARG→ENV antes de `npm run build`, y `build.args` explícito en compose) | La URL base es build-time por naturaleza (SPA estática, `import.meta.env.*`); el ARG lo hace explícito y reproducible; los defaults `5002` del código quedan solo como fallback de `npm run dev` (sin cambios). |
| D4 | **`appsettings.json`: `Jwt:Key` → `""`** | Hace alcanzable el throw `"JWT Key is not configured"` de `Program.cs` (hoy el literal lo enmascara); fallo explícito en cualquier entorno sin `Jwt__Key`. |
| D5 | **`.dockerignore`** en `workflow/frontend` (`node_modules`, `dist`, `.env*`) y `workflow/backend` (`bin`, `obj`, `*.db`, `appsettings.*.local`) | `COPY . .` arrastra binarios del host (node_modules glibc) y artefactos locales → contexto de build sucio y riesgo de imágenes no reproducibles. |
| D6 | **Mantener volumen nombrado `database_data`** | Cambio a bind mount (para acceso de MCPs del host) **excluido** de US-007: es un cambio de contrato de datos con riesgo de pérdida; se registra como mejora futura en DECISIONS.md. |
| D7 | **Chatbot sin cambios** | Ya alineado (puerto, health, requirements). `LLM_API_KEY` futura excluida (regla no-placeholders). |
