# User Story — US-016 — Configurar LLM local Ollama en el chatbot, empaquetar los 3 MCP en la imagen del chatbot y corregir CORS

*(Possible statuses: Draft, Planned, Approved, In Progress, Implemented, Validated, Rejected)*

## User Story

Como usuario de la biblioteca, quiero que el chatbot use el modelo local Ollama llama3.2 para sus recomendaciones (manteniendo GROQ solo para la auditoría de Security-Audit-MCP), que los servidores MCP queden empaquetados dentro de la imagen Docker del chatbot para que funcionen bajo docker compose, y que se corrija el bloqueo CORS que impide al frontend comunicarse con el chatbot, para que el asistente responda correctamente en el aplicativo desplegado

---

## Functional Description

El chatbot FastAPI (LangGraph) debe generar sus recomendaciones en lenguaje natural con el modelo local **Ollama llama3.2** (endpoint compatible con OpenAI), en lugar del proveedor cloud de OpenAI. La auditoría de entrada/salida de Security-Audit-MCP **continúa usando exclusivamente GROQ** (`API_KEY_GROQ`). Los tres servidores MCP (Biblioteca-MCP, Security-Audit-MCP, Open Library MCP) deben quedar empaquetados dentro de la imagen Docker del chatbot para que los comandos `BIBLIOTECA_MCP_COMMAND`, `SECURITY_AUDIT_MCP_COMMAND` y `OPEN_LIBRARY_MCP_COMMAND` resuelvan a rutas válidas dentro del contenedor bajo `docker compose up`. Finalmente, el chatbot debe exponer la cabecera CORS correcta para que la SPA (origen del frontend, p. ej. `http://localhost:5173`) pueda llamar a `POST /chat` y `GET /health` desde el navegador sin errores.

### Comportamiento esperado

1. **Recomendaciones con Ollama llama3.2 (local).** El nodo `llm_response` redacta la recomendación personalizada con Ollama vía `ChatOpenAI` apuntando a la URL base local (`OLLAMA_BASE_URL`), con modelo `OLLAMA_MODEL` (`llama3.2`). GROQ no interviene en las recomendaciones. Si Ollama no está disponible o falla, se conserva el fallback heurístico del nodo `response` (ADR-023: el chatbot nunca colapsa).
2. **MCP empaquetados en la imagen del chatbot.** La imagen del chatbot incluye el código de los 3 MCP (y el paquete `common/`), sus dependencias (`fastmcp`, `httpx`) y expone comandos stdio ejecutables dentro del contenedor. Los archivos SQLite (`DATABASE_PATH`, `AUDIT_DATABASE_PATH`) se resuelven a rutas absolutas dentro del contenedor compartidas con el backend mediante volumen. Open Library MCP usa el servidor local empaquetado (no `npx`), evitando Node en la imagen.
3. **CORS corregido.** El chatbot agrega FastAPI `CORSMiddleware` con orígenes permitidos leídos de `CORS_ORIGINS` (sin valores por defecto, ADR-025), permitiendo el preflight OPTIONS y las cabeceras `Content-Type` y `X-Correlation-ID` usadas por el frontend.

  When el usuario envía un mensaje malicioso (intento de prompt injection)

  And el nodo llm_response de Ollama NO intervino en el bloqueo

Scenario: Biblioteca-MCP funciona dentro del contenedor del chatbot
  Given la imagen del chatbot contiene biblioteca-mcp y sus dependencias
  And BIBLIOTECA_MCP_COMMAND apunta a un comando válido dentro de la imagen
  And DATABASE_PATH resuelve a la base SQLite real del catálogo (volumen compartido)
  When el usuario pregunta por libros del catálogo
  Then el chatbot devuelve resultados del catálogo interno vía Biblioteca-MCP sin "MCP no disponible"

Scenario: Open Library MCP funciona dentro del contenedor del chatbot
  Given la imagen del chatbot contiene open-library-mcp y sus dependencias
  And OPEN_LIBRARY_MCP_COMMAND apunta al servidor local empaquetado
  When el usuario pide libros de un autor y el catálogo interno se enriquece
  Then el chatbot consulta Open Library vía MCP y devuelve resultados enriquecidos

Scenario: Security-Audit-MCP funciona dentro del contenedor del chatbot
  Given la imagen del chatbot contiene security-audit-mcp y sus dependencias
  And SECURITY_AUDIT_MCP_COMMAND apunta a un comando válido dentro de la imagen
  And AUDIT_DATABASE_PATH es escribible desde el contenedor
  When el usuario envía un mensaje cualquiera por el chat
  Then la entrada y la salida son auditadas por Security-Audit-MCP y el flujo termina en HTTP 200

Scenario: docker compose up arranca sin errores de MCP
  Given el .env con los 3 *_MCP_COMMAND apuntando a rutas válidas dentro de la imagen del chatbot
  When se ejecuta docker compose up --build y el usuario envía un mensaje
  Then el contenedor del chatbot arranca sin fallar por comandos MCP inexistentes
  And el mensaje recibe una respuesta del asistente

Scenario: El frontend llama al chatbot sin bloqueo CORS
  Given la SPA servida en el origen del frontend (http://localhost:5173) y el chatbot en http://localhost:8000, ambos bajo docker compose
  When el usuario abre el widget de chat y envía un mensaje
  Then la petición POST /chat se completa con HTTP 200
  And no aparecen errores CORS en la consola del navegador

Scenario: El preflight OPTIONS del navegador es respondido correctamente
  Given el navegador va a enviar POST /chat con Content-Type: application/json y el header custom X-Correlation-ID
  When el navegador dispara la petición preflight OPTIONS
  Then el chatbot responde con los headers CORS permitiendo el origen del frontend (Access-Control-Allow-Origin, -Methods, -Headers)
  And la petición POST posterior se ejecuta sin errores

Scenario: El origen no permitido no queda habilitado
  Given el chatbot configurado para permitir únicamente el/los origen(es) del frontend definidos por configuración
  When una petición llega desde un origen distinto al permitido
  Then el chatbot no incluye los headers CORS para ese origen y el navegador bloquea la respuesta

## Technical Plan

### 1. Integración de Ollama (LLM local para recomendaciones)

- **Cliente:** mantener `langchain_openai.ChatOpenAI` (ya depende `langchain-openai`); apuntarlo a la URL base de Ollama (`OLLAMA_BASE_URL`, p. ej. `http://ollama:11434/v1` en compose o `http://host.docker.internal:11434/v1` en desarrollo de host). No se añade `langchain-ollama`/`ChatOllama` (dependencia nueva innecesaria).
- **Nuevas variables de entorno** (patrón ADR-025, sin valores por defecto en código):
  - `OLLAMA_BASE_URL` — opcional en código; si se define, el cliente la usa. En compose es obligatoria (`:?`).
  - `OLLAMA_MODEL` — requerido (fail-fast `RuntimeError`) si `OLLAMA_BASE_URL` está definida. Compose la fija a `llama3.2`.
  - `LLM_API_KEY` / `LLM_MODEL` — se mantienen como vía cloud opcional (ADR-023) con prioridad menor que Ollama.
  - `LLM_TIMEOUT_SECONDS` — **nueva**, requerida cuando el LLM está habilitado (evita que el timeout fijo de 20s mate a llama3.2 en CPU). Compose la fija a `120`.
- **Prioridad de proveedor en `app/llm/client.py`:**
  1. Si `OLLAMA_BASE_URL` está definida → `ChatOpenAI(model=_ollama_model(), base_url=_ollama_base_url(), api_key="ollama", temperature=0.4, max_tokens=300, timeout=_llm_timeout())`. El placeholder `api_key="ollama"` no es secreto (Ollama lo ignora; el cliente OpenAI exige clave no vacía).
  2. Si no, si `LLM_API_KEY` está definida → vía cloud actual sin cambios.
  3. Si no → `None` → el grafo usa el fallback heurístico `response` (ADR-023 preservado).
- **Fallback:** excepción en `model.ainvoke` (Ollama caído, timeout, modelo no cargado) → el `except Exception: return None` existente en `generate_recommendation` dispara el fallback. PII masking (`mask_pii`) se mantiene obligatorio antes de llamar al proveedor.
- **GROQ intocable:** `workflow/mcp/security-audit-mcp/groq_audit.py` conserva `API_KEY_GROQ`, `GROQ_MODEL=llama-3.3-70b-versatile`, `GROQ_API_URL`, `GROQ_TIMEOUT_SECONDS`. Ninguna ruta del LLM de recomendaciones usa GROQ.

### 2. Empaquetado de los 3 MCP en la imagen del chatbot

- **Contexto de build:** `docker-compose.yml` → `chatbot.build.context: .` y `chatbot.build.dockerfile: workflow/chatbot/Dockerfile` (Docker `COPY` no puede escapar del contexto; los MCP viven en `workflow/mcp/`).
- **Nuevo `.dockerignore` raíz** (obligatorio para que el build desde la raíz no envíe todo el repo): incluir `node_modules/`, `.venv/`, `**/__pycache__`, `.git`, `*.db`, `*.sqlite`, `.env`, `dist/`, `bin/`, `obj/`; permitir `workflow/chatbot/` y `workflow/mcp/`.
- **`workflow/chatbot/Dockerfile`:** copiar `workflow/chatbot` a `/app` y `workflow/mcp` a `/app/workflow/mcp` (preservar el prefijo `workflow/` para que `parents[3]` de `workflow/mcp/common/settings.py` y el bootstrap `sys.path.insert(0, REPO_ROOT / "workflow" / "mcp")` sigan resolviendo sin cambios de código). `pip install --no-cache-dir` de los requirements del chatbot + los 3 MCP (añañadir `fastmcp>=0.2.0` a `workflow/chatbot/requirements.txt`; `httpx` ya está).
- **Comandos MCP in-image (en compose y `.env`):**
  - `BIBLIOTECA_MCP_COMMAND=python /app/workflow/mcp/biblioteca-mcp/server.py`
  - `SECURITY_AUDIT_MCP_COMMAND=python /app/workflow/mcp/security-audit-mcp/server.py`
  - `OPEN_LIBRARY_MCP_COMMAND=python /app/workflow/mcp/open-library-mcp/server.py` — servidor local empaquetado (no `npx -y mcp-open-library`): evita Node en la imagen, está versionado en el repo y ya pasa CI.
- **Rutas de base de datos en el contenedor:**
  - `DATABASE_PATH=/app/database/BibliotecaVirtual.db`
  - `AUDIT_DATABASE_PATH=/app/database/audit.db`
  - El volumen `database_data:/app/database` ya montado en el backend se añade al servicio `chatbot` (mismo archivo SQLite que el backend crea con `EnsureCreated`; `registrar_feedback` escribe por ADR-022). Se añade `depends_on: backend` para orden de arranque (la BD existe antes de las peticiones MCP; si no, el fallback degrada con elegancia).
- **Ollama en compose:** nuevo servicio `ollama` (imagen `ollama/ollama`, puerto `11434`, volumen `ollama_data:/root/.ollama`); un pequeño paso de inicialización ejecuta `ollama serve` y `ollama pull "$OLLAMA_MODEL"` al primer arranque (entrada de shell en el servicio). El chatbot recibe `OLLAMA_BASE_URL=http://ollama:11434/v1` y `depends_on: ollama`. Alternativa de desarrollo documentada: Ollama en el host + `OLLAMA_BASE_URL=http://host.docker.internal:11434/v1` con `extra_hosts: ["host.docker.internal:host-gateway"]`.

### 3. Corrección de CORS

- **`workflow/chatbot/main.py`:** añadir FastAPI `CORSMiddleware`.
  - `allow_origins` = `_cors_origins()` parseando `CORS_ORIGINS` (separadas por coma), fail-fast `RuntimeError` si falta (ADR-025, sin default).
  - `allow_methods=["POST","GET"]`; `allow_headers=["Content-Type","X-Correlation-ID"]`; `allow_credentials=False` (el frontend no envía cookies/Authorization al chatbot; el JWT es solo backend y `userId` viaja en el body).
  - El preflight OPTIONS lo maneja el middleware automáticamente.
- **Variable reutilizada:** `CORS_ORIGINS` (ya existe en `.env.example` y compose para el backend con valor `http://localhost:5173`) — una sola fuente de verdad para el origen de la SPA.
- **compose chatbot:** añadir `- CORS_ORIGINS=${CORS_ORIGINS:?Set CORS_ORIGINS in the .env file (e.g. http://localhost:5173)}`.

### 4. Tests
