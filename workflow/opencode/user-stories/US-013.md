# User Story — US-013 — Notificaciones automáticas de vencimiento de alquileres mediante BackgroundService

*(Possible statuses: Draft, Planned, Approved, In Progress, Implemented, Validated, Rejected)*

## User Story

Como sistema backend, quiero ejecutar un BackgroundService en .NET que detecte los alquileres que están a dos días de vencer y genere una notificación automática en la tabla correspondiente, para que los usuarios reciban avisos oportunos de vencimiento sin intervención manual.

---

## Functional Description

El sistema backend ejecuta un proceso periódico (`BackgroundService` de .NET) que escanea los alquileres **activos** y detecta aquellos cuya fecha de vencimiento (`DueDate`) cae dentro de la ventana de **2 días desde la fecha actual**. Para cada alquiler detectado, se genera una fila en una nueva tabla `Notifications`, asociada al usuario que tiene el alquiler.

Capacidades funcionales:

1. **Ventana temporal:** un alquiler activo se considera «próximo a vencer» cuando `0 < DueDate - Now <= 2 días`. Alquileres ya vencidos (`DueDate <= Now`) o con más de 2 días de margen quedan fuera de la ventana.
2. **Estado del alquiler:** solo se consideran alquileres con `Status = Active` (no devueltos ni vencidos).
3. **Idempotencia:** el servicio es idempotente. Si ya existe una notificación para el mismo alquiler (`RentalId`), no se crea una duplicada en ejecuciones posteriores.
4. **Contenido de la notificación:** mensaje en español con el título del libro y la fecha límite (ej. «Tu alquiler de "Cien años de soledad" vence el 20/08/2026. Devuélvelo a tiempo»).
5. **Lectura:** las notificaciones se generan con `IsRead = false`. El usuario las consulta y marca como leídas vía API.
6. **Endpoints REST:** `GET /api/notifications` (mis notificaciones, permiso `notifications.read`) y `PATCH /api/notifications/{notificationId}/read` (marcar como leída). Los controllers se limitan a despachar al `Dispatcher` (CQRS).
7. **Permiso:** se siembra el permiso `notifications.read` en los roles `Admin`, `Bibliotecario` y `Usuario` y se registra la policy correspondiente.
8. **Intervalo configurable:** el periodo de ejecución del servicio se lee de configuración (`Notifications:CheckIntervalSeconds`, sobreescribible por la variable de entorno `NOTIFICATIONS_CHECK_INTERVAL_SECONDS`).
9. **Envío fuera de alcance:** la notificación es una fila en BD. El envío real (email/websocket/push) queda fuera de esta historia.
10. **UI de campana fuera de alcance:** el desarrollo de la campana/panel de notificaciones en el frontend se pospone a una historia futura; esta historia entrega los endpoints para consumir las notificaciones.

## Acceptance Criteria

```gherkin
Scenario: Alquiler a dos días de vencer genera notificación
Given un alquiler con Status = 'Active'
And DueDate dentro de la ventana (0 < DueDate - Now <= 2 días)
When el BackgroundService se ejecuta
Then se crea una fila en la tabla Notifications para ese alquiler
And la notificación queda con IsRead = false y el mensaje incluye el título del libro y la fecha límite

Scenario: Segunda ejecución no duplica la notificación
Given una notificación ya generada para un alquiler activo dentro de la ventana
When el BackgroundService se ejecuta de nuevo
Then no se crea una nueva fila en Notifications para ese alquiler

Scenario: Alquileres fuera de la ventana no generan notificación
Given un alquiler activo con DueDate a más de 2 días
And un alquiler activo ya vencido (DueDate <= Now)
When el BackgroundService se ejecuta
Then no se genera ninguna notificación para esos alquileres

Scenario: El usuario consulta sus notificaciones
Given un usuario autenticado con permiso notifications.read
When solicita GET /api/notifications
Then recibe solo sus notificaciones con id, mensaje, fecha límite, estado de lectura y fecha de creación

Scenario: El usuario marca una notificación como leída
Given una notificación de un usuario con IsRead = false
When el mismo usuario solicita PATCH /api/notifications/{id}/read
Then la notificación queda con IsRead = true
And un usuario distinto no puede marcar esa notificación
```

## Technical Plan

### D1. Decisiones técnicas (Technical Lead)

1. **Entidad `Notification` en el Dominio:** nueva entidad en `Domain/Entities/Notification.cs` con `Id (Guid)`, `UserId (Guid)`, `RentalId (Guid)`, `Message (string)`, `DueDate (DateTime)`, `IsRead (bool)`, `CreatedAt (DateTime)`. Relación con `User` (FK `UserId`, `OnDelete Cascade`) y con `Rental` (FK `RentalId`, `OnDelete Cascade`). Índice único sobre `RentalId` para garantizar idempotencia a nivel de esquema.
2. **`BackgroundService` en Infrastructure que despacha un Command:** el proceso periódico (`RentalDueNotificationService`) no contiene lógica de negocio; cada ciclo crea un scope (via `IServiceScopeFactory`) y despacha `GenerateDueDateNotificationsCommand` por el `IDispatcher` (ADR-009). El handler contiene la detección de la ventana y la inserción idempotente.
3. **CQRS estricto (Dispatcher propio):** todos los artefactos usan `BaseCommand<TResponse>`/`BaseQuery<TResponse>`, `ICommandHandler<>`/`IQueryHandler<>` con `HandleAsync`, registrados en `DependencyInjection.cs`. **Prohibido** `MediatR` y `IMapper` (AutoMapper no existe en el proyecto; se usa `NotificationMapper` estático siguiendo el patrón de `RentalMapper`).
4. **Validación FluentValidation:** `MarkNotificationReadCommand` y `GetMyNotificationsQuery` tienen validators; el Command interno `GenerateDueDateNotificationsCommand` no recibe entrada de usuario y no requiere validator.
5. **Permiso y policy:** se añade `notifications.read` al seed de roles `Admin`, `Bibliotecario` y `Usuario` en `Program.cs` (mismo patrón que `rentals.view_own`), y la policy `notifications.read` en `AddAuthorization`.
6. **Intervalo configurable:** `Notifications:CheckIntervalSeconds` en `appsettings.json` (valor por defecto 3600s = 1 hora), sobreescribible por env `NOTIFICATIONS_CHECK_INTERVAL_SECONDS` en docker-compose (ADR-016).
7. **Alcance frontend:** la UI de notificaciones (campana) es una historia futura; esta historia entrega `GET /api/notifications` y `PATCH /api/notifications/{id}/read` para consumirlas.
8. **Chatbot/MCP sin cambios:** los avisos por chat (`due_reminder`/`overdue`) siguen funcionando; la tabla `Notifications` es un mecanismo backend adicional.

### D2. Backend (.NET 9)

**Nuevos archivos:**

1. `workflow/backend/src/Domain/Entities/Notification.cs` — entidad del dominio.
2. `workflow/backend/src/Application/Contracts/Notifications/NotificationContracts.cs` — records:
   - `NotificationResponse(Guid Id, Guid UserId, Guid RentalId, string Message, DateTime DueDate, bool IsRead, DateTime CreatedAt)`.
   - `GenerateDueDateNotificationsResult(int CreatedCount)`.
3. `workflow/backend/src/Application/Commands/Notifications/GenerateDueDateNotificationsCommand.cs` — `sealed record : BaseCommand<GenerateDueDateNotificationsResult>` (sin entrada de usuario).
4. `workflow/backend/src/Application/Commands/Notifications/MarkNotificationReadCommand.cs` — `sealed record(Guid NotificationId, Guid UserId) : BaseCommand<bool>`.
5. `workflow/backend/src/Application/Commands/Notifications/Validators/MarkNotificationReadCommandValidator.cs` — `NotificationId` y `UserId` no vacíos.
6. `workflow/backend/src/Application/Queries/Notifications/GetMyNotificationsQuery.cs` — `sealed record(Guid UserId, int Page = 1, int PageSize = 20, bool? UnreadOnly = null) : BaseQuery<PagedResult<NotificationResponse>>`.
7. `workflow/backend/src/Infrastructure/Handlers/Notifications/GenerateDueDateNotificationsCommandHandler.cs` — detecta alquileres `Active` con `Now < DueDate <= Now.AddDays(2)`, excluye los que ya tienen notificación (`RentalId` existente), inserta filas con mensaje en español (título del libro + fecha límite), retorna `CreatedCount`.
8. `workflow/backend/src/Infrastructure/Handlers/Notifications/MarkNotificationReadCommandHandler.cs` — valida que la notificación exista y pertenezca a `UserId`; marca `IsRead = true`; retorna `false` si no es del usuario o no existe.
9. `workflow/backend/src/Infrastructure/Handlers/Notifications/GetMyNotificationsQueryHandler.cs` — paginado (mismo patrón que `GetMyRentalsQueryHandler`) con filtro opcional `UnreadOnly`, ordenado por `CreatedAt` descendente.
10. `workflow/backend/src/Infrastructure/Handlers/Notifications/NotificationMapper.cs` — `Notification → NotificationResponse`.
11. `workflow/backend/src/Infrastructure/Services/RentalDueNotificationService.cs` — `BackgroundService` con `PeriodicTimer`, lee `Notifications:CheckIntervalSeconds`, por ciclo crea scope y despacha `GenerateDueDateNotificationsCommand`; logging de resumen y manejo de errores sin romper el loop; `StopAsync`/`CancellationToken`.
12. `workflow/backend/src/WebAPI/Controllers/NotificationsController.cs` — controller delgado:
    - `GET api/notifications` → `[Authorize(Policy = "notifications.read")]`, despacha `GetMyNotificationsQuery(UserId, ...)`.
    - `PATCH api/notifications/{notificationId:guid}/read` → `[Authorize(Policy = "notifications.read")]`, despacha `MarkNotificationReadCommand(notificationId, UserId)`; `404` si `false`.

**Archivos modificados:**

1. `workflow/backend/src/Infrastructure/Data/BibliotecaDbContext.cs` — `DbSet<Notification> Notifications` + configuración Fluent (longitudes, relaciones, índice único `RentalId`).
2. `workflow/backend/src/Infrastructure/DependencyInjection.cs` — registrar handlers de Command/Query, validator y `services.AddHostedService<RentalDueNotificationService>()`.
3. `workflow/backend/src/WebAPI/Program.cs` — policy `notifications.read`; añadir `notifications.read` al seed de `Admin`, `Bibliotecario`, `Usuario`.
4. `workflow/backend/src/WebAPI/appsettings.json` — sección `Notifications: { "CheckIntervalSeconds": 3600 }`.
5. `docker-compose.yml` — variable `NOTIFICATIONS_CHECK_INTERVAL_SECONDS` (opcional con valor por defecto) en el servicio `backend`.

**Nota operativa:** el proyecto usa `EnsureCreated`; al eliminar una sola vez `workflow/database/BibliotecaVirtual.db` se regenera el esquema con la tabla `Notifications` (el seed de catálogo es idempotente, ADR-019).
