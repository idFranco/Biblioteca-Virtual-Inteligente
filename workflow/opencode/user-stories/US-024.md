# User Story — US-024 — Tolerar el sufijo de tag (:latest) en el match del modelo Ollama de la validación de arranque y /health

*(Possible statuses: Draft, Planned, Approved, In Progress, Implemented, Validated, Rejected)*

## User Story

Como administrador del proyecto, quiero que la validación de arranque (app/startup_checks.py) y el /health del chatbot consideren cargado el modelo local Ollama cuando OLLAMA_MODEL se configura sin tag pero Ollama lo reporta con tag por defecto (p. ej. llama3.2 == llama3.2:latest), manteniendo el match exacto cuando el tag se especifica explícitamente (llama3.2:13b) para que docker compose up --build no rechace el modelo local como 'no cargado' y el fail-fast informe el estado real de las dependencias.

---

## Functional Description

La validación de arranque fail-fast de US-023 (`python -m app.startup_checks`, entrada del CMD del Dockerfile del chatbot) compara `OLLAMA_MODEL` contra el id de los modelos que Ollama devuelve en `GET {OLLAMA_BASE_URL}/models` mediante un **match exacto de string** (`model not in ids`, `startup_checks.py:85`).

Ollama identifica cada modelo como `<name>:<tag>`, donde el tag por defecto es `latest`. Con `OLLAMA_MODEL=llama3.2` (config válida y usada por el cliente LLM, `app/llm/client.py`, que resuelve a `llama3.2:latest`), el check acierta el error "El modelo local Ollama no está cargado" aunque `llama3.2:latest` esté cargado (p. ej. `100% GPU`), bloqueando `docker compose up --build` con un falso negativo. Idem para `/health` (usa la misma `check_ollama()` vía `probe_health()`), que reporta `ollama: down` con el modelo sano.

Esta historia normaliza la comparación: `OLLAMA_MODEL` sin tag se considera cargado si existe un modelo disponible con el mismo nombre base (ignorando el tag, p. ej. `llama3.2` ≡ `llama3.2` o `llama3.2:latest`); si se configura con tag explícito (`llama3.2:13b`), el match es exacto. El diagnóstico de error se conserva. No cambia variables de entorno ni el comportamiento del cliente LLM.

## Technical Plan

### 1. `workflow/chatbot/app/startup_checks.py` — normalizar el match del modelo Ollama

En `check_ollama()`, reemplazar el match exacto (`startup_checks.py:85`) por una comparación que ignore el tag `:tag` de Ollama cuando `OLLAMA_MODEL` no lo trae:

- Helper `_ollama_model_loaded(model: str, available_ids: list[str]) -> bool`:
  - Si `model` contiene `:` → match exacto (`model in available_ids`), preservando el comportamiento actual para tags explícitos (`llama3.2:13b`).
  - Si `model` no contiene `:` → se considera cargado si algún id disponible es `model` o empieza por `model + ":"` (p. ej. `llama3.2` y `llama3.2:latest` → True; `llama3.2:13b` con `OLLAMA_MODEL=llama3.2` → True, pues el tag explícito también es el mismo modelo base).
- El mensaje de error se conserva: `El modelo local Ollama no está cargado: '{model}' no aparece en '{url}' (modelos disponibles: ...)`.
- La normalización convive con el diagnóstico: no se altera `_ollama_base_url()`, `_ollama_model()`, `check_groq()`, `probe_health()` ni la caché TTL.
- Impacto: corrige `check_ollama()` (fail-fast del CMD) y `probe_health()` (`/health`, que la invoca).

```python
def _ollama_model_loaded(model: str, available_ids: list[str]) -> bool:
    if ":" in model:
        return model in available_ids            # tag explícito: match exacto
    return model in available_ids or any(
        mid.startswith(f"{model}:") for mid in available_ids
    )
```

Uso en `check_ollama()`:

```python
ids = [item.get("id") for item in (payload.get("data") or [])]
if not _ollama_model_loaded(model, ids):
    raise RuntimeError(...)
```
