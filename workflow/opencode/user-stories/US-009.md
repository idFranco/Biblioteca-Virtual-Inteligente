# User Story — US-009 — Integración Open Library MCP: enriquecimiento de catálogo y solicitud de copias

*(Possible statuses: Draft, Planned, Approved, In Progress, Implemented, Validated, Rejected)*

## User Story

Como usuario, quiero que el sistema obtenga datos de Open Library (vía su MCP) para enriquecer la disponibilidad del catálogo y, cuando un libro requerido no exista en la base de datos, poder solicitar una copia que estará disponible pronto; y como administrador, quiero gestionar esas solicitudes (Gestión de Libro) para dar de alta los libros solicitados en el catálogo, ampliando así la disponibilidad con fuentes externas.

---

## Functional Description

- **Enriquecimiento del catálogo desde Open Library (vía MCP):** El catálogo puede ampliarse con metadatos bibliográficos obtenidos de Open Library a través del MCP externo (`open-library`, implementado en `workflow/mcp/open-library-mcp/` y activado en `opencode.json` al validar US-009 — ADR-014). Los metadatos recuperados (título, autor, ISBN, género, descripción, clave de obra, portada) se incorporan a la base de datos para que el libro quede disponible en el catálogo. Conforme a `ADR-007`, el frontend **nunca** invoca MCP directamente: la obtención de metadatos de Open Library se realiza por el grafo del chatbot (`external_enrichment_node`) contra el servidor MCP, y los metadatos se persisten como snapshot en la solicitud de copia para que el backend los materialice sin depender del MCP en tiempo de alta.
- **Flujo de solicitud de copia (evolución del chat, prompt 6):** Cuando el usuario pregunta por un libro al chatbot:
  1. `internal_catalog_node` busca el libro en la base de datos vía `Biblioteca-MCP` (`buscar_libros`).
  2. Si **no existe**, `external_enrichment_node` consulta Open Library MCP para obtener metadatos del libro.
  3. Si el usuario confirma la opción **"Solicitar copia (estará disponible pronto)"**, el frontend (ChatWidget) envía `POST /api/book-requests` **con el JWT del usuario** y el snapshot de Open Library: se crea un `BookRequest` en `Pending`. El chatbot **nunca escribe la BD ni maneja el JWT** (ADR-011: el acceso a datos no pasa por el chatbot; el backend es la única autoridad de autorización).
  4. Si el libro **sí existe** en el catálogo, el chatbot deriva al flujo normal (recomendación/alquiler) y **no** crea solicitudes.
  5. Si Open Library no responde o no encuentra el libro (Bug 2), el chatbot responde amablemente (fallback) sin colapsar el grafo y sin crear solicitud. Todo el flujo es auditado por `Security-Audit-MCP` (entrada y salida), usa memoria persistente vía `Biblioteca-MCP` y propaga `X-Correlation-ID`.
- **Flujo de "Gestión de Libro" (administrador):** Nueva sección de gestión donde el Admin y el Bibliotecario (permiso `books.manage`) pueden:
  - **Listar solicitudes:** consultar todas las solicitudes de copia paginadas, con filtro por estado y búsqueda por título/autor, incluyendo el snapshot de Open Library, el solicitante y la fecha.
  - **Ver detalle:** revisar la información bibliográfica capturada de Open Library.
  - **Aprobar / dar de alta:** crear el libro real en el catálogo (`Book`) a partir de los metadatos de la solicitud, indicando el número de copias (`TotalCopies ≥ 1`, `AvailableCopies = TotalCopies`). Reutiliza `CreateBookCommand` despachado internamente vía `IDispatcher`. La solicitud pasa a `Approved` con `PromotedBookId`.
  - **Rechazar:** marcar la solicitud como `Rejected` indicando un motivo obligatorio; el solicitante puede ver el estado y el motivo en sus propias solicitudes.
- **Permisos involucrados:** se introducen dos permisos nuevos de la familia `books.*` (claims `permission` + policies):
  - `books.request` — crear solicitudes de copia y consultar las propias (roles `Admin`, `Bibliotecario` y `Usuario`).
  - `books.manage` — Gestión de Libro: listar todas las solicitudes, aprobar (promover a catálogo) y rechazar (roles `Admin` y `Bibliotecario`).
  - `books.create` (existente) — requerido para materializar el alta del libro (se reutiliza la lógica ya validada de US-004).
  - Sin token → `401`; token sin el permiso requerido → `403`.
- **Reglas de negocio y validación:** no se permite solicitud duplicada `Pending` para el mismo usuario y mismo libro (mismo ISBN o mismo título+autor normalizado); no se crea solicitud si el libro ya existe en el catálogo; el alta exige `TotalCopies ≥ 1` y `AvailableCopies = TotalCopies`; los metadatos de Open Library son referenciales y el administrador puede corregirlos/cambiarlos antes del alta; toda solicitud se valida con FluentValidation antes de procesarse.

## Technical Plan

### Backend (.NET 9 — Clean Architecture + CQRS Dispatcher + FluentValidation)

1. **Domain**
   - Nuevo `Domain/Enums/BookRequestStatus.cs`: `enum BookRequestStatus { Pending, Approved, Rejected }`.
   - Nueva `Domain/Entities/BookRequest.cs`: `Id (Guid)`, `Title (string, req, ≤255)`, `Author (string, req, ≤255)`, `Isbn? (≤20)`, `Genre? (≤100)`, `Description? (≤2000)`, `OpenLibraryKey? (≤64)`, `RequestedBy (Guid, FK → User)`, `RequestedAt (DateTime = UtcNow)`, `Status (BookRequestStatus = Pending)`, `AdminNotes? (≤500)`, `PromotedBookId? (Guid?, FK → Book)`, `ResolvedAt?`. Navegaciones `RequestedByUser` y `PromotedBook`.
   - Modificar `Domain/Entities/Book.cs`: añadir `string? OpenLibraryKey { get; set; }` (trazabilidad de fuente externa).
2. **Application**
   - `Contracts/BookRequests/BookRequestContracts.cs` (records): `BookRequestResponse` (incluye `OpenLibraryKey`, `PromotedBookId`, `RequestedByEmail`), `CreateBookRequestRequest`, `ApproveBookRequestRequest` (overrides opcionales + `TotalCopies`), `RejectBookRequestRequest` (`AdminNotes` obligatoria).
   - `Commands/BookRequests/`: `CreateBookRequestCommand`, `ApproveBookRequestCommand`, `RejectBookRequestCommand` (todos `BaseCommand<BookRequestResponse>` con `CorrelationId`).
   - `Queries/BookRequests/`: `GetBookRequestsQuery(Page, PageSize, Status?, Search?)`, `GetMyBookRequestsQuery(UserId, Page, PageSize, Status?)`, `GetBookRequestByIdQuery(Id, UserId, CanViewAll)`.
   - Validators FluentValidation: `CreateBookRequestCommandValidator` (título/autor requeridos ≤255, ISBN ≤20, género ≤100, OpenLibraryKey ≤64), `ApproveBookRequestCommandValidator` (`TotalCopies` en [1,1000], overrides opcionales con límites), `RejectBookRequestCommandValidator` (`AdminNotes` obligatoria ≤500). Limites consistentes con `CreateBookCommandValidator`.
   - Modificar `Commands/Books/CreateBookCommand.cs` para aceptar `OpenLibraryKey` opcional (primer paso de la promoción).
3. **Infrastructure**
   - `Data/BibliotecaDbContext.cs`: `DbSet<BookRequest> BookRequests` + configuración (título/autor requeridos, `Status` con `HasConversion<string>()` + índice, FK `RequestedBy → Users` con `DeleteBehavior.Restrict`, FK `PromotedBookId → Books` con `Restrict`).
   - `Handlers/BookRequests/`: `CreateBookRequestCommandHandler` (guarda duplicado: Book existente mismo ISBN/título+autor → 409; BookRequest `Pending` idéntico → 409), `ApproveBookRequestCommandHandler` (carga, exige `Pending` → 409 si resuelta, **despacha `CreateBookCommand` vía `IDispatcher`** con metadata efectiva (overrides ?? snapshot) y `TotalCopies`, marca `Approved` + `PromotedBookId` + `ResolvedAt`), `RejectBookRequestCommandHandler`, `GetBookRequestsQueryHandler` (paginado, filtro status/search, join `Users` para email), `GetMyBookRequestsQueryHandler`, `GetBookRequestByIdQueryHandler` (ownership: si `!CanViewAll && RequestedBy != UserId` → 401), `BookRequestMapper`.
   - `DependencyInjection.cs`: registrar handlers y validators nuevos.
4. **WebAPI**
   - Nuevo `Controllers/BookRequestsController.cs` (delgado, `[ApiController]`, solo `IDispatcher`):
     - `POST /api/book-requests` → `books.request` → 201.
     - `GET /api/book-requests/mine` → `books.request` (solicitudes propias paginadas).
     - `GET /api/book-requests` → `books.manage` (listado paginado, filtro status/search).
     - `GET /api/book-requests/{id}` → `books.request`/`books.manage` (ownership).
     - `POST /api/book-requests/{id}/approve` → `books.manage` (`ApproveBookRequestRequest` con `TotalCopies` ≥1).
     - `POST /api/book-requests/{id}/reject` → `books.manage` (`RejectBookRequestRequest`).
   - `Program.cs`: en `AddAuthorization` añadir policies `"books.request"` y `"books.manage"` (`RequireClaim("permission", ...)`); en `SeedRolesAsync` añadir: **Admin** → `books.request`, `books.manage`; **Bibliotecario** → `books.manage` (ya gestiona catálogo); **Usuario** → `books.request`.
   - Auditoría estructurada Who/What/When para crear/aprobar/rechazar (solo metadatos, sin PII).
5. **Datos**: al usar `EnsureCreated`, la BD de desarrollo se regenera (los `.db` no se versionan).

### Open Library MCP — `workflow/mcp/open-library-mcp/`

1. Servidor FastMCP propio que envuelve la API REST de Open Library (SSR/libsearch) vía `httpx`:
   - Tool `ol_search_books(query)` → lista de resultados (title, author, isbn, key/OLID, cover).
   - Tool `ol_get_book_details(key)` → detalle (descripción, subjects/género, portada).
   - Base URL configurable por env, sin secretos hardcodeados, errores estructurados, timeout.
2. `opencode.json`: actualizar entrada `open-library` a `"enabled": true` **al validar US-009** (ADR-014). El chatbot lo consume por stdio (mismo comando `npx -y mcp-open-library` o el path local).
3. Docker: si se requiere contenedor propio, añadir servicio en `docker-compose.yml` (ADR-013) y variable `OPEN_LIBRARY_MCP_COMMAND` al servicio `chatbot`.
